# eBible.org 新改訳新約聖書(1965年版) 본문 스크래핑 개발 설계

## 1. 목적

`https://ebible.org/jpn1965/`의 **新改訳新約聖書(1965年版)**(New Japanese NT, 이하 NJNT) **신약 27권**을 스크래핑하여 기존 PostgreSQL 스키마(`bible_chapter`, `bible_verse`)에 적재한다.

### 1.1 이 문서가 다루는 범위

[일본어 퍼블릭 도메인 설계 문서](japanese-public-domain-scraping-design.md)에서 후보를 조사할 때, eBible.org의 일본어 항목이 둘뿐임을 확인했다. 하나는 이미 적재를 마쳤다.

| eBible ID | 이름 | 범위 | 상태 |
| --- | --- | --- | --- |
| `jpnm` | フリーダム・バイブル | 구약+신약 | **적재 완료** (`translation_id=36`, `JPNMEB`) |
| `jpn1965` | 新改訳新約聖書(1965年版) | **신약만** | 이 문서 |

앞 문서는 `jpn1965`를 "**신약뿐이라 66권을 채울 수 없다**"는 이유로 제외하고 별도 설계로 미뤘다. 이 문서가 그 별도 설계다.

> 앞 문서 초안이 `jpn1965`를 `restricted`(배포 제한)로 적었던 것은 **오류**였다. find 페이지의 인접 행 class를 잘못 집은 것이고, 실제 행은 `redist`이며 details 페이지도 `public domain`이다. 앞 문서는 정정했다.

### 1.2 배포처 표기 (실측)

```
新改訳新約聖書(1965年版)  New Japanese NT
Language: [jpn] 日本語   Abbreviation: NJB   ID: JPNLOC or jpn1965
public domain
The New Testament in Japanese, 1965 Shinkaiyaku seisho (New Japanese Bible) translation
```

find 페이지의 해당 `<tr>` class는 `redist`(재배포 가능)다.

> **판본을 혼동하면 안 된다.** 新改訳은 현재도 개정이 이어지는 계열(1970 초판, 제2판, 제3판, 2017)이며 **현행판은 신일본성서간행회의 저작물**이다. 여기서 다루는 것은 배포처가 퍼블릭 도메인으로 표기한 **1965년 신약 판본에 한정**된다. 이 문서는 법률 자문이 아니며, 위 내용은 배포처 표기를 조회한 결과다.

## 2. 결론 먼저

1. **URL·HTTP·인코딩·재시도·resume·CJK 공백 처리는 변경 0줄.** `jpnm`과 같은 사이트·같은 렌더러다. 엔트리 URL만 `https://ebible.org/jpn1965/MAT01.htm`으로 주면 된다.
2. **DOM이 세 소스 중 가장 단순하다.** `div.p`와 `span.verse`뿐이고 `div.q`·`div.d`·`div.sp`·`span.wj`·`a.notemark`가 **표본에서 전부 0건**이다. 표제·각주·시가 관련 규칙이 발동할 여지가 없다.
3. **파서에 수정이 필요하다.** 이 소스는 **절을 병합**해 표시한다. 마커 라벨은 범위(`37-38`)인데 `id`에는 앞 번호만 들어 있어, 현재 파서는 뒤 번호를 통째로 잃는다. 260개 장 전수 조사 결과 **병합 18건 / 사라지는 절 19개**([4.3](#43-함정-1-절이-병합되어-표시된다)).
4. **병합 절을 어떻게 저장할지는 미결정이다.** 본문 내용을 바꾸는 결정이라 적재 전에 정해야 한다([4.4](#44-미결정-병합-절을-어떻게-저장할-것인가)).
5. **27권만 적재된다.** 저장소는 66권을 전제하므로 `bible_book` 시드와 검증 기준을 신약으로 좁혀야 한다. `fetch_books()`는 존재하는 행만 반환하므로 **파이프라인 코드 자체는 수정이 필요 없다**([6.4](#64-bible_book-27권-시드), [7.1](#71-구조-검증--기준이-달라진다)).
6. **`translation_type`을 `NJB`로 쓰면 안 된다.** 배포처 공식 약칭이지만 **New Jerusalem Bible**과 통용 약칭이 겹친다. `JPNMEB` 선례대로 eBible 공식 ID인 **`JPNLOC`**을 권고한다([5.2](#52-scrape_bible_to_dbpy--역본-등록)).
7. **책명은 `div.mt`와 `ul.tnav`가 완전히 일치**하고 둘 다 27권 고유하다. `jpnm`에서 `div.mt`가 결함이었던 것과 다르다.

## 4. 대상 페이지 특성

### 4.1 URL 규칙 — 기존과 동일, 다만 신약만

```
https://ebible.org/jpn1965/{USFM대문자}{장번호:02d}.htm
```

신약에는 100장 이상인 책이 없으므로 **장 번호는 항상 2자리**다(시편 3자리 패딩 규칙은 발동하지 않는다). 기존 `_build_ebible_chapter_segment()`가 그대로 적용된다.

```
source = ebible | code = jpn1965 | version = jpn1965
```

**구약 39권은 404다.** `discover_chapter_urls_for_book()`은 `KJV_CHAPTER_COUNTS`로 URL을 만들 뿐 존재를 확인하지 않으므로, `bible_book`에 구약을 시드하면 39권 전부가 실패한다. **시드를 신약으로 한정하는 것이 사실상의 방어선이다**([6.4](#64-bible_book-27권-시드)).

### 4.2 DOM 구조 — 세 소스 중 가장 단순

```html
<div class="main">
  <div class="mt">マタイの福音書</div>
  <div class="p">
    <span class="verse" id="V1">1&#160;</span>本文...
    <span class="verse" id="V2">2&#160;</span>本文...
  </div>
</div>
```

| 클래스 | jpnm | jpn1965 | 처리 |
| --- | --- | --- | --- |
| `div.p` | 장당 4~19 | 장당 1~11 | 본문 |
| `div.q` / `div.q2` | 시가서 전반 | **0건** | 해당 없음 |
| `div.b` (연 구분) | 관측 | **35건** | 텍스트가 없어 무해. 전권 집계로 확인 |
| `div.d` / `div.sp` | 관측 | **0건** | 해당 없음 |
| `a.notemark` / `span.popup` | 관측 | **0건** | 해당 없음 |
| `span.wj` | 관측 | **0건** | 해당 없음 |
| `ruby` / `rt` | 0건 | **0건** | 해당 없음 |

즉 **표제 제거·각주 2단계 제거·`(omitted)` 판정이 모두 무발동**이다. 기존 규칙이 해를 끼치지 않으므로 그대로 둔다.

260개 장 전권 클래스 집계(실측):

```
div.p 1167   span.verse 7939   div.mt 27   div.b 35
div.q / div.q2 / div.d / div.sp / span.wj / a.notemark / span.popup / ruby : 전부 0
```

> 초안은 표본 13개 장만 보고 `div.b`도 0건이라고 적었으나 **전권에는 35건 있다.** `div.b`는 연 구분용 빈 블록이라 텍스트가 없어 파싱에 영향이 없지만, 표본으로 "0건"을 단정하면 안 된다는 사례다.

> `(omitted)` 처리가 발동하지 않는다는 것은 **이 소스가 원문 이문을 각주가 아니라 절 병합으로 표기**하기 때문이다([4.3](#43-함정-1-절이-병합되어-표시된다)).

### 4.3 함정 1. 절이 병합되어 표시된다

**이 문서에서 가장 중요한 항목이다.**

마커의 **표시 라벨은 범위**인데 **`id`는 그 범위를 담지 못한다.**

```html
<span class="verse" id="V37">37-38&#160;</span>そして馬車を止めさせ、…バプテスマを授けた。
<span class="verse" id="V39">39&#160;</span>水から上がって来たとき、…
```

기존 파서는 `id`만 읽으므로 이 항목을 **절 37**로 저장하고, **절 38은 존재하지 않게 된다.** 260개 장 전수 조사 결과:

```
장 수: 260 (기대 260)      마커 총 개수: 7,939
병합 마커: 18건            병합으로 사라지는 절: 19개
병합 크기: 2절 17건, 3절 1건
라벨이 숫자도 범위도 아닌 경우: 0건
```

병합 위치 18건 전부:

```
MRK07 16-17   MRK09 44-45   MRK09 46-47   MRK11 26-27   MRK15 28-29
LUK01 1-2     LUK01 74-75   LUK11 51-52   LUK17 36-37   LUK23 17-18
LUK24 40-41   JHN05 4-5     ACT08 37-38   ACT15 34-35   ACT24 7-8
ACT28 29-30   ROM02 19-20   ROM16 24-26
```

#### `id`는 신뢰할 수 없다 — 라벨이 권위 있는 출처다

대부분의 장에서 `id`는 범위의 앞 번호와 일치하지만 **예외가 있다.** 병합이 있는 16개 장을 전수 확인한 결과 마가복음 9장에서 어긋난다.

```
id=V44   라벨='44-45'
id=V45   라벨='46-47'    <- id 는 45 인데 라벨은 46-47
id=V48   라벨='48'
```

한 장에 병합이 둘 있을 때 `id` 카운터가 밀린 것으로 보인다. 결과적으로 **현재 파서는 46~47절 본문을 45절에 저장한다** — 번호가 통째로 틀린다. 뒤 번호가 빠지는 것보다 나쁘다.

따라서 수정은 "`id`를 보완한다"가 아니라 **"라벨이 있으면 라벨을 쓴다"**여야 한다.

**라벨 기준으로 확장하면 병합이 있는 16개 장 전부가 1부터 연속**이 된다(실측). 라벨이 올바른 출처라는 직접 증거다.

```
MRK07 마커36 -> 확장37 연속O      ACT08 마커39 -> 확장40 연속O
MRK09 마커48 -> 확장50 연속O      ROM16 마커25 -> 확장27 연속O
... 16개 장 전부 연속 O
```

#### 병합의 성격 — WEB의 이문 집합으로는 분류되지 않는다

처음에는 "본문 이문"과 "번역상 병합" 두 갈래로 나누려 했으나, **WEB의 `(omitted)` 집합으로는 분류되지 않는다.** 18건 중 WEB이 앞 번호를 `(omitted)`로 표기한 것은 **4건뿐**이다.

```
[WEB 이 (omitted) 로 표기] 4건
   LUK 17:36-37   ACT 8:37-38   ACT 15:34-35   ACT 24:7-8
   -> jpnm 이 (omitted) 로 처리한 바로 그 네 절이다

[WEB 앞 번호에 본문이 있음] 14건
   MRK 7:16-17  MRK 9:44-45  MRK 9:46-47  MRK 11:26-27  MRK 15:28-29
   LUK 1:1-2    LUK 1:74-75  LUK 11:51-52 LUK 23:17-18  LUK 24:40-41
   JHN 5:4-5    ACT 28:29-30 ROM 2:19-20  ROM 16:24-26
```

뒤 14건 안에도 사본상 논란이 있는 위치(막 9:44·46, 막 11:26, 막 15:28, 눅 23:17, 요 5:4, 행 28:29, 롬 16:24)와 순수한 번역상 병합(눅 1:1-2, 눅 1:74-75, 눅 11:51-52, 롬 2:19-20)이 섞여 있다. WEB이 이문을 본문으로 포함하는 편집 방침이라 경계가 겹치지 않는다.

**저장 방식 결정에 이 분류는 필요하지 않다.** 아래 B안은 두 유형을 동일하게 처리하며, 라벨이 가리키는 번호 전체가 그 본문을 갖는다는 사실은 어느 쪽이든 같다.

**이 손실은 자동 검증 일부를 통과한다.** 빈 절도 없고 첫 절은 1이다. 다만 **절 번호 연속성 검사에는 걸린다** — 저장소가 그 검사를 불변식으로 삼는 이유가 여기서 드러난다.

### 4.4 미결정. 병합 절을 어떻게 저장할 것인가

DB는 절 단위인데 소스는 범위 단위다. 본문 내용을 바꾸는 결정이므로 **적재 전에 정해야 한다.**

| 안 | 내용 | 평가 |
| --- | --- | --- |
| A | 현재 동작 유지 — `id` 번호에만 저장 | **채택 불가.** 19개 절이 사라져 연속성 불변식이 깨지고, 막 9장에서는 `id`가 밀려 **46~47절 본문이 45절에 들어간다** |
| **B** | **범위의 모든 번호에 같은 본문을 저장** | 연속성 유지. 절 조회가 항상 옳은 내용을 돌려준다. 본문이 중복되지만 원문이 실제로 그 범위를 한 단위로 다룬다는 사실과 어긋나지 않는다 |
| C | 앞 번호에 본문, 나머지에 포인터 표기(`(37-38 합본)`) | 연속성 유지, 중복 없음. 그러나 조회 측이 표기를 해석해야 하고, 막 9장처럼 `id`와 라벨이 어긋나면 "앞 번호"라는 전제가 깨진다 |
| D | 이 역본을 적재하지 않는다 | 병합이 18건뿐이라 과도하다 |

**B를 권고한다.** 근거는 셋이다.

- 저장소의 불변식(절 번호 연속)을 지키면서 **어떤 절 번호로 조회해도 올바른 본문**이 나온다. 라벨 기준 확장이 16개 장 전부에서 1부터 연속이 됨을 실측했다.
- 원문이 그 범위를 **한 단위로 조판**했다는 사실을 왜곡하지 않는다. 중복은 그 사실의 반영이다.
- WEB `(omitted)`가 "원문에 본문이 없다"를 표기한 것과 달리, 여기는 **본문이 있고 경계만 다르다.** `(omitted)`류 표기는 사실과 맞지 않는다.
- C안은 "앞 번호에 본문"을 전제하는데, 막 9장처럼 `id`와 라벨이 어긋나면 그 전제 자체가 성립하지 않는다.

구현은 파서에서 **마커 라벨의 범위를 읽어** `id` 대신 사용하는 것이다.

```python
# 마커 라벨이 "37-38" 형태면 그 범위 전체를 이 항목이 덮는다. id 는 앞 번호만 담으므로
# 라벨을 읽지 않으면 뒤 번호가 통째로 사라진다(jpn1965 에서 19개 절).
EBIBLE_VERSE_RANGE_PATTERN = re.compile(r"^\s*(\d{1,3})\s*[-–]\s*(\d{1,3})\b")
```

- 라벨이 범위가 아니면 기존 `id` 기반 동작을 그대로 쓴다. **다른 eBible 역본에 영향이 없어야 한다.** 실측으로 확인했다 — `jpn1965`에서 병합이 나온 장과 같은 위치를 세 역본에서 조사한 결과 **범위 라벨 0건**이다.

```
spablm      검사 19장 / 범위 라벨 0건
spaRV1909   검사 19장 / 범위 라벨 0건
jpnm        검사 19장 / 범위 라벨 0건
```
- 범위의 끝이 시작보다 작거나 폭이 비상식적으로 크면(예: 10 초과) 파싱 오류로 보고 **범위를 무시**한다. 조용히 수십 개 절을 복제하는 것보다 낫다.

> 이 결정은 [7.5](#75-병합-절-검증)의 기대값을 좌우한다. B안이면 총 절 수가 **7,958**이 되고, A안이면 7,939다.

## 5. 코드 변경 지점

### 5.1 `scraper.py` — 범위 라벨 해석 (유일한 파서 변경)

`_extract_verses_from_ebible_page()`에서 마커를 만날 때, `id`로 얻은 번호와 함께 **라벨의 범위**를 읽어 둔다. 본문 누적이 끝난 뒤 범위에 속한 모든 번호에 같은 본문을 넣는다([4.4](#44-미결정-병합-절을-어떻게-저장할-것인가) B안).

주의할 점:

- **라벨이 범위면 라벨이 이긴다.** `id`는 막 9장에서 실제로 어긋나므로 보조 수단으로만 쓴다. 라벨이 단일 숫자일 때만 기존 `id` 경로를 쓴다.
- `(omitted)` 판정과 충돌하지 않아야 한다. 이 소스에는 각주가 없어 실제로는 무발동이지만, 다른 eBible 역본에서 각주만 있는 마커가 범위 라벨을 갖는 경우를 배제할 수 없다. **각주 판정이 우선**이다.
- CJK 공백 규칙은 그대로 뒤에 적용된다.

### 5.2 `scrape_bible_to_db.py` — 역본 등록

```python
ENTRY_URL_ENV_BY_TRANSLATION_TYPE = { ..., "JPNLOC": "JPNLOC_ENTRY_URL" }
TRANSLATION_TYPES_BY_LANGUAGE_CODE = { ..., "ja": ("JPNMEB", "JPNLOC") }
ENTRY_URL_PREFERENCE_ORDER = (..., "JPNMEB", "JPNLOC")
TRANSLATION_SOURCE_REQUIREMENTS = {
    ...,
    "JPNLOC": {
        "source": "ebible",
        "version": "jpn1965",
        "name": "新改訳新約聖書(1965年版)",
        "language_code": "ja",
    },
}
```

**`translation_type`은 `NJB`가 아니라 `JPNLOC`을 쓴다.** `NJB`는 배포처 공식 약칭이지만 **New Jerusalem Bible**의 통용 약칭과 겹친다. 직전 작업에서 `JFB`(Jamieson-Fausset-Brown 주석과 혼동 소지)를 eBible 공식 ID `JPNMEB`로 바꾼 것과 같은 판단이다.

이 등록으로 `ja`에 역본이 둘이 되므로, `BIBLE_LANGUAGE_CODE=ja` 단독 지정은 **두 엔트리 URL이 모두 설정된 경우 모호해져 예외**가 된다(`en`·`es`와 같은 동작). README에 명시한다.

`scraper.py`에 기본 엔트리 URL 상수도 추가한다.

```python
DEFAULT_EBIBLE_JPNLOC_ENTRY_URL = "https://ebible.org/jpn1965/MAT01.htm"
```

## 6. DB 준비

### 6.1 현재 상태 (실측)

```
[bible_translation]        30행. ja: JPNMEB(id=36) 1건
[translation_type CHECK]   30개 값, 'JPNLOC' 없음
[bible_book_description]   en 66 / es 66 / ja 66 / ko 66   <- ja 이미 존재
[language_code CHECK]      ko, en, zh, ja, es, de, la
```

### 6.2 `translation_type` CHECK 제약 — 31번째 값

RVR1909(27→28), SBLM(28→29), JPNMEB(29→30) 때와 동일한 절차다. `pg_get_constraintdef()`로 현재 정의를 **프로그램으로 읽어** 값을 추가하고, 재생성 후 개수와 유실을 확인한다.

### 6.3 `bible_translation` row

```sql
INSERT INTO public.bible_translation (translation_type, name, language_code, translation_order)
SELECT 'JPNLOC', '新改訳新約聖書(1965年版)', 'ja',
       COALESCE(MAX(translation_order), 0) + 1
FROM public.bible_translation;
```

`translation_order`는 NOT NULL이고 기본값이 없으며 `id`를 따라가지 않는다. `name`·`translation_type`에 UNIQUE가 걸려 있고 기존 값과 충돌하지 않는다.

### 6.4 `bible_book` **27권** 시드

**이 문서에서 가장 큰 구조적 차이다.** 저장소는 66권을 전제하지만 이 역본은 신약뿐이다.

- `book_order`는 **40~66**을 쓴다. 정경 순서를 유지해야 다른 역본과 대조가 된다.
- **구약 39권을 시드하면 안 된다.** 시드하면 `discover_chapter_urls_for_book()`이 존재하지 않는 URL을 만들고, 39권이 전부 실패해 `--book-retries`만 소모한다.
- `fetch_books(conn, 1, 66)`은 존재하는 행만 반환하므로 **27권만 시드하면 파이프라인은 그대로 돈다.** 코드 수정이 필요 없다.

책명은 `ul.tnav`와 `div.mt`가 **완전히 일치**하고 둘 다 27종 고유하다(`jpnm`에서 `div.mt`가 9권을 2개 이름으로 뭉갰던 것과 다르다). 어느 쪽을 써도 되며, 일관성을 위해 `ul.tnav`를 쓴다.

```
40 MAT  マタイの福音書      44 ACT  使徒の働き
41 MRK  マルコの福音書      64 3JN  ヨハネの手紙第三
42 LUK  ルカの福音書        65 JUD  ユダの手紙
43 JHN  ヨハネの福音書      66 REV  ヨハネの黙示録
```

`abbreviation`과 `testament_type`은 NOT NULL이다. JPNMEB 때와 같이 `abbreviation`은 `book_key`를 쓰고, `testament_type`은 전부 `NEW`다(기존 역본에서 복사해도 된다).

> **CLAUDE.md의 "66권이 모두 존재한다고 가정한다"는 계약이 이 역본에서는 성립하지 않는다.** 계약 문구를 "대상 `translation_id`에 존재하는 책만 읽는다. 신약 전용 역본은 27권만 시드한다"로 보완한다.

### 6.5 `bible_book_description` — 추가 작업 없음

`(book_key, language_code)` 키이고 `ja` 66행이 JPNMEB 작업에서 이미 적재됐다. **신규 삽입 0행**이다.

## 7. 검증

### 7.1 구조 검증 — 기준이 달라진다

66권/1,189장 기준을 그대로 쓰면 안 된다.

| 항목 | 전권 역본 | **이 역본** |
| --- | --- | --- |
| 책 | 66 | **27** (`book_order` 40~66) |
| 장 | 1,189 | **260** |
| 절 | 역본별 | **7,958** (B안 기준, [7.5](#75-병합-절-검증)) |

나머지(절이 0개인 장 없음, 절 번호 1부터 연속, 빈 본문 없음)는 동일하게 적용한다.

```sql
-- book_order 가 40 미만인 행이 있으면 구약을 잘못 시드한 것이다 (기대값 0)
SELECT COUNT(*) FROM public.bible_book
WHERE translation_id = :tid AND book_order < 40;
```

### 7.2 인코딩 검증

JPNMEB와 동일하다. **일본어 문자가 하나도 없는 절**을 세는 것이 주 검사이고, 스페인어용 mojibake 패턴(`Ã`/`Â`)은 일본어에 걸리지 않으므로 `ã`/`ä`/`å`를 본다. 이 역본에는 `(omitted)` 표기가 없으므로 제외 조건이 필요 없다.

```sql
SELECT COUNT(*) FROM public.bible_verse v
JOIN public.bible_chapter c ON c.id = v.chapter_id
JOIN public.bible_book b    ON b.id = c.book_id
WHERE b.translation_id = :tid
  AND v.text !~ '[぀-ヿ一-鿿]';
-- 기대값: 0
```

### 7.3 CJK 공백 검증

표본에서는 0건이었지만(`div.p` 하나에 여러 절이 들어가 블록 경계가 드물다) 전권에서는 확인해야 한다. 쿼리는 [JPNMEB 설계 문서](japanese-public-domain-scraping-design.md) 7.3과 동일하다.

### 7.4 기존 역본 대조

**절 번호 체계가 KJV 쪽이다.** 로마서 16장 최대 절 번호를 보면 분명하다.

```
KJV      27       <- jpn1965 과 같다
WEB      24
JPNMEB   25
jpn1965  27  (마커 V27, 24-26 병합)
```

따라서 **대조 기준은 WEB이 아니라 KJV(`translation_id=10`)**로 잡는다. 신약 절 수도 KJV 7,957이다.

차이가 곧 누락은 아니다. 이 역본은 병합 때문에 KJV보다 절 수가 많거나 적을 수 있으므로, 차이 항목은 [7.5](#75-병합-절-검증)의 병합 목록과 대조해 설명이 붙는지 확인한다.

### 7.5 병합 절 검증

B안을 채택하면 **병합 범위의 모든 번호에 같은 본문**이 들어간다. 이를 직접 확인한다.

```sql
-- 병합으로 본문이 같아야 하는 쌍 (예: 사도행전 8:37 과 8:38)
SELECT v.verse_number, LEFT(v.text, 40)
FROM public.bible_verse v
JOIN public.bible_chapter c ON c.id = v.chapter_id
JOIN public.bible_book b    ON b.id = c.book_id
WHERE b.translation_id = :tid AND b.book_key = 'ACT' AND c.chapter_number = 8
  AND v.verse_number IN (37, 38);
-- 기대: 두 행의 text 가 동일
```

기대 총량은 **적재 전에 전권 시뮬레이션으로 확정했다.**

```
검사 장 수: 260
범위 확장 후 총 절 수: 7,958
확장 후에도 1부터 연속이 아닌 장: 0건
```

마커 7,939개 + 병합으로 늘어나는 19개 = **7,958절**이고, 260개 장 전부가 1부터 연속이 된다. **7,958이 아니거나 비연속 장이 하나라도 나오면 원인을 밝히기 전에는 적재를 완료로 보지 않는다.** 병합 18건의 위치는 [4.3](#43-함정-1-절이-병합되어-표시된다)에 전부 적어 두었으므로 대조가 가능하다.

## 8. 테스트 설계

`tests/test_scraper.py`에 인라인 HTML 픽스처로 추가한다(**네트워크 접근 금지**).

| 테스트 | 검증 내용 |
| --- | --- |
| `..._expands_merged_verse_range` | 라벨 `37-38`이 절 37과 38 **둘 다**에 같은 본문으로 들어간다 |
| `..._expands_three_verse_range` | 라벨 `24-26`이 세 번호로 확장된다 |
| `..._ignores_range_when_id_missing` | `id`가 없거나 형식이 다르면 기존대로 건너뛴다 |
| `..._ignores_implausible_range` | `38-37`이나 폭이 과도한 범위는 무시한다 |
| `..._keeps_plain_numbers_unchanged` | 범위가 아닌 마커는 기존 동작 그대로다 |
| `..._does_not_expand_in_other_ebible_translations` | spablm/spaRV1909 픽스처가 영향을 받지 않는다 |
| `..._builds_jpn1965_urls` | 엔트리 URL이 `jpn1965`면 URL이 그 경로로 생성된다 |
| `..._separates_four_ebible_translations` | eBible 네 번째 역본이 정합성 검증에서 구분된다 |

마지막 두 개가 회귀 방지의 핵심이다. 범위 해석이 다른 역본에 새는 순간 조용히 본문이 복제된다.

## 9. 운영 계획

### 9.1 요청 간격과 소요

`ebible.org`에 `Crawl-delay` 선언이 없으므로 자체 하한 1.0초를 유지한다. **260장 기준 약 8분**으로 전권 역본(35분)보다 짧다.

### 9.2 실행 예

```bash
# 파서만 확인 (DB 미접속)
JPNLOC_ENTRY_URL=https://ebible.org/jpn1965/MAT01.htm BIBLE_TRANSLATION_TYPE=JPNLOC \
python3 scrape_bible_to_db.py --test-book 44 --test-chapter 8

# 신약 전권
BIBLE_TRANSLATION_ID=<tid> BIBLE_TRANSLATION_TYPE=JPNLOC BIBLE_LANGUAGE_CODE=ja \
JPNLOC_ENTRY_URL=https://ebible.org/jpn1965/MAT01.htm \
python3 scrape_bible_to_db.py --start-book 40 --end-book 66
```

`--start-book 1`로 실행해도 `bible_book`에 27권만 있으면 동작은 같다. 다만 **의도를 드러내기 위해 40~66을 명시**한다.

### 9.3 갱신 문제

`jpnm`·`spablm`과 달리 이 역본은 **1965년 확정 판본**이며 초안 표기가 없다. 그래도 배포처가 파일을 재생성할 수 있으므로, 확인은 같은 도구를 쓴다.

```bash
python3 scripts/check_translation_drift.py --translation-id <tid> \
  --entry-url https://ebible.org/jpn1965/MAT01.htm --start-book 40 --end-book 66
```

재적재 절차(절 → 장 순서 삭제)는 [SBLM 설계 문서](santa-biblia-libre-para-el-mundo-scraping-design.md) 9.3절과 동일하다.

## 11. 리스크

### 리스크 1. 범위 해석이 다른 역본으로 샌다 (가장 큼)

파서는 eBible 세 역본이 공유한다. 범위 라벨 해석이 spablm·spaRV1909·jpnm에서 오작동하면 **본문이 조용히 복제**된다. → [8](#8-테스트-설계)에 타 역본 무영향 테스트를 넣고, 적재 후 세 역본에 `check_translation_drift.py`를 돌려 차이 0을 확인한다.

### 리스크 2. 구약을 잘못 시드

`bible_book`에 66권을 시드하면 구약 39권이 전부 404로 실패한다. 실패 자체는 드러나지만 재시도로 시간을 소모하고, 부분 적재 상태가 남는다. → [7.1](#71-구조-검증--기준이-달라진다)의 `book_order < 40` 쿼리를 시드 직후에 실행한다.

### 리스크 3. 병합 저장 방식 번복

[4.4](#44-미결정-병합-절을-어떻게-저장할-것인가). B안과 C안은 저장 내용이 다르고 missing-only 삽입이라 번복하면 재적재다. → 착수 전에 확정한다.

### 리스크 4. 신약 전용 역본을 전권 역본처럼 검증

66권/1,189장 기준을 그대로 쓰면 정상인데도 실패로 읽힌다. 반대로 27권/260장을 기대값으로 굳히면 구약 누락을 못 본다. → 검증 스크립트에 **역본이 신약 전용인지 명시적으로 넘긴다.**

### 리스크 5. 판본 혼동

新改訳은 현행판이 저작권 보호를 받는 계열이다([1.2](#12-배포처-표기-실측)). `jpn1965` 이외의 경로에서 가져온 데이터를 섞으면 안 된다. → 엔트리 URL을 `jpn1965`로 고정하고, 정합성 검증이 `version=jpn1965`를 요구하도록 등록한다([5.2](#52-scrape_bible_to_dbpy--역본-등록)).

## 12. 결론

이 역본은 **소스 추가가 아니라 역본 추가**이며, eBible 어댑터의 URL·HTTP·인코딩·재시도·resume·CJK 공백 처리가 그대로 재사용된다. DOM은 세 소스 중 가장 단순해 표제·각주·시가 규칙이 아예 발동하지 않는다.

그러나 **다른 세 eBible 역본에 없던 구조가 하나 있다** — 절 병합이다. 260장 전수 조사로 18건 / 19개 절을 확인했고, 현재 파서는 이를 잃는다. 더 나쁜 것은 마가복음 9장처럼 **`id`와 라벨이 어긋나는 경우**로, 46~47절 본문이 45절에 저장된다. 따라서 라벨을 권위 있는 출처로 삼아야 한다.

실제로 필요한 작업은 셋이다.

1. **범위 라벨 해석** — 유일한 파서 변경. 다른 eBible 역본에 새지 않는 것이 핵심이다.
2. **역본 등록** — `translation_type`은 공식 약칭 `NJB`가 아니라 eBible 공식 ID **`JPNLOC`**을 쓴다. `NJB`는 New Jerusalem Bible과 겹친다.
3. **DB 시드** — CHECK 제약 1개, `bible_translation` 1행, `bible_book` **27행**(신약만). `bible_book_description`은 추가 작업 없음.

착수 전 확인이 필요한 사항은 하나다 — **병합 절 저장 방식**([4.4](#44-미결정-병합-절을-어떻게-저장할-것인가)). 나머지는 결론이 나 있다.
