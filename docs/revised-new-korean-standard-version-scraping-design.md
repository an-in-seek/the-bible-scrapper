# 대한성서공회(`bskorea.or.kr`) 새번역(RNKSV) 본문 스크래핑 개발 설계

## 1. 목적

`bskorea.or.kr`의 **성경전서 새번역**(2001) 본문을 수집해 DB의 `RNKSV` 행(`bible_translation.id = 3`)에 66권 전 구절을 적재하는 설계다.

- 예시 URL
  - `https://www.bskorea.or.kr/bible/korbibReadpage.php?version=SAENEW&book=gen&chap=1&sec=1&cVersion=&fontSize=15px&fontWeight=normal`
  - `https://www.bskorea.or.kr/bible/korbibReadpage.php?version=SAENEW&book=psa&chap=3&sec=1&cVersion=&fontSize=15px&fontWeight=normal`
  - `https://www.bskorea.or.kr/bible/korbibReadpage.php?version=SAENEW&book=jnh&chap=1&sec=1&cVersion=&fontSize=15px&fontWeight=normal`
- 판본 이름: 이 사이트는 **표준새번역**(1993, `version=SAE`)과 그 개정판인 **새번역**(2001, `version=SAENEW`)을 별개 역본으로 제공한다. 처음 요청은 "표준새번역"이었다. 두 판이 다르고 DB에는 새번역 자리(`RNKSV`)만 있다는 점을 알린 뒤, 사용자가 **새번역 2001**로 정했다(2026-10-29). 1993년 표준새번역은 대상이 아니다. 그 판을 넣으려면 `translation_type` CHECK에 새 값을 추가하고 `bible_translation` 행을 새로 만들어야 한다(이 문서 범위 밖).

새번역은 [개역개정(NKRV)](nkrv-scraping-design.md)과 **같은 소스, 같은 URL 규칙, 같은 파서**를 쓴다. 이 문서는 NKRV 문서를 반복하지 않고 새번역에서 달라지는 점과, 그 과정에서 찾은 **현재 bskorea 경로의 결함**을 다룬다. 그대로 유효한 항목은 아래와 같다.

- `korbibReadpage.php` URL 생성. `version`은 엔트리 URL에서 이어받는다(`_build_bskorea_url`)
- 본문 루트 `#tdBible1.bible_read`, 비교 역본(`tdBible2`) 배제
- `span.number`·`a.comment`·`div.D2`·`display:none` 제거, 인라인 `font` 텍스트 보존
- `get_text("")` (조사 띄어쓰기 버그 방지)
- 장 단위 커밋, missing-only insert, `bible_book` 비생성 계약

## 2. 권리 — 대한성서공회 저작물이다

**새번역은 퍼블릭 도메인이 아니다.** 저작권자는 대한성서공회이고, 이미 적재된 개역개정과 처지가 같다. 이 문서는 "표준새번역 성경 스크래핑 설계" 요청(2026-10-29)에 따라 설계와 표본 실측을 했고, 이어서 사용자가 "구현까지만"을 골라(2026-10-30) 코드 변경·테스트·DB 미접속 smoke test까지 했다(15절). **적재는 하지 않았다.** 아래 표는 2026-10-29에 대한성서공회 페이지를 직접 읽어 확인한 내용이다.

| 항목 | 확인 내용 (2026-10-29) |
| --- | --- |
| 저작권자 (저작권안내, `co_id=subpage2_3_4_1`) | 대한성서공회. "한글성경의 2차 저작물 저작권자"이며, 이용하려면 이용 허락을 받고 저작권료를 내야 한다고 밝힌다 |
| 보호기간 | 같은 페이지의 표가 "공표된 때부터 70년"이라 적고, **성경전서 새번역 — 2001년 11월 10일 발행**을 목록에 둔다. 소멸 표시는 없다. 공표 다음 해부터 세면 **2071년 말까지**다(이 문서의 계산). 같은 표에서 개역한글판(1961)은 2011-12-31에 저작재산권 보호기간이 소멸했다 |
| 허가조건 및 사용료 (`co_id=subpage2_3_4_3`) | "컴퓨터 성경"(PC·모바일 웹을 통한 성경 본문 서비스 포함) **번역본당 100만 원, 허가기간 1년**. "성경 어플리케이션"은 기본 100만 원에 다운로드 수에 따른 금액이 더해진다 |
| 이용약관 (`co_id=provision`) | 금지 행위로 "대한성서공회와 기타 제3자의 저작권 등 지적재산권에 대한 침해", "동의 없이 영리를 목적으로 서비스를 사용하는 행위"를 든다. 회원은 "서비스를 이용하여 취득한 정보를 임의 가공, 판매하는 행위 등 … 상업적으로 사용할 수 없다"(제14조 2항). 자동 수집(크롤링)을 직접 다루는 조항은 찾지 못했다 |
| `robots.txt` | **없다**(404). `Crawl-delay` 선언도 없다 |
| 문의처 | 02-2103-8730, `kbscopyright@bskorea.or.kr` |
| 이 설계의 적재량 | 66권 전 구절. 개역개정(id 2)과 같은 규모다 |

정리하면 다음과 같다.

- **설계와 표본 실측은 적재 없이 했다.** 표본은 구조 분석에만 쓰고 DB에 넣지 않았다.
- **전권 적재는 대한성서공회 허가 대상이다.** 적재(10절)는 별도 게이트로 둔다. 실행 여부는 이 표를 보고 사용자가 정한다. 개역개정을 이미 같은 방식으로 적재했다는 사실은 허가 여부를 바꾸지 않는다.
- `attribution` 후보는 개역개정 행의 형식을 따른 `성경전서 새번역 © 대한성서공회`다. 허가를 받지 않았으므로 "허락을 받아 사용" 같은 문구는 넣지 않는다.
- 이 문서는 새번역 본문을 인용하지 않는다. DOM 예시는 구조만 보이고 본문 자리는 `(본문)`으로 표시한다. 편집 표지(`(21절 없음)`, `(여자)` 등)와 책 이름은 본문이 아니므로 그대로 적는다.

## 3. 결론 먼저

**지금 코드로 새번역을 적재하면 안 된다.** 배선(정합성 검증 표 한 행)만 추가하면 적재는 돌아가지만, 표본 67개 장에서 아래 결함이 나왔다. 어느 것도 적재기의 가드(빈 장, 첫 절이 1이 아닌 장)에 걸리지 않는다. 요나와 생략 절은 적재 후 KJV 절 수 대조에서 드러나지만, 나머지는 그 대조도 통과한다.

| --- | --- | --- |
| 요나서 책 코드 `jon` | 빈 페이지 → 범용 파서가 장마다 **1절짜리 쓰레기 절**을 만든다 (5.1) | **수정함 (2026-10-30)** — bskorea 코드는 `jnh` |

## 4. 실측 (2026-10-29)

### 4.1 표본

- 새번역 67개 장. 저장소 스크래퍼의 요청 경로를 그대로 쓰고 요청 간격만 3~6초로 올렸다(`raise_delay_floor(3)`). 재시도는 끄고, 오류가 나면 멈추도록 했다. 오류와 제한 페이지는 한 번도 없었다
- 고른 기준: 히브리어·영어 장절 경계가 갈리는 곳(창 31–32, 출 8·22, 레 6, 민 16–17, 신 12·29, 삼상 20·24, 삼하 19, 왕상 4–5, 대상 6, 느 4, 욥 41, 전 5, 아 1·6·7, 사 9·64, 겔 21, 단 4–6, 호 1·14, 욜 2–3, 욘 1–2, 미 5, 말 4), 시편 표제(시 3·18·51·119·150), 비평 본문이 빼는 절과 논란 본문(마 12·17·18·23, 막 7·9·11·15·16, 눅 17·23, 요 5·7·8, 행 8·15·19·24·28, 롬 14·16, 고후 13, 요일 5, 요삼, 계 12–13)
- 추가 요청: 요나 1장을 `jnh`로 한 번, 개역개정 대조용으로 `GAE` 6개 장(삼하 19, 행 8, 시 3, 시 92, 신 6, 마 17)과 `GAE` 요나 1장(`jon`) 한 번. 2026-10-30에는 NKRV에 빠진 좌표가 있는 `GAE` 9개 장(신 15·30, 대상 16, 시 105, 렘 32·33, 겔 24, 행 15, 롬 9)을 더 받았다(5.7)

### 4.3 KJV·NKRV 대조

시제품 파서(6.7) 결과를 DB의 KJV(10)·NKRV(2) 절 번호와 장마다 비교했다.

- 장절 경계는 **KJV(영어식)와 같다.** 위 4.1의 경계 장에서 절 수가 모두 KJV와 같다. 요나는 `jon`으로 받아 빈 페이지였고(5.1), 1장만 `jnh`로 다시 받아 17절(KJV와 같음)을 확인했다. 요나 2장은 측정하지 못했다
- KJV에만 있는 좌표: **생략 14절**(5.5)과 **고후 13:14**(13:13에 합쳐짐, 장 끝이라 구멍이 아님)
- 새번역에만 있는 좌표: **요삼 1:15**(NKRV도 같다), **계 12:18**(NKRV에는 없다. KJV 13:1 앞부분이 12:18로 간다. 새번역 계 13장도 18절이다)
- 생략 14절: 마 17:21, 18:11, 23:14 / 막 9:44, 9:46, 11:26, 15:28 / 눅 17:36, 23:17 / 행 8:37, 15:34, 24:7, 28:29 / 롬 16:24. **DB의 NKRV가 생략 자리표시를 둔 14곳과 좌표가 정확히 같다**(12곳은 `(없음)`, 나머지 둘은 글자가 다르다. 5.5, 7절)
- NIV·ESV가 빼는 16절 중 **막 7:16, 요 5:4는 새번역에 있다.** 요 5:3 하반–5:4는 `[ ]`로 묶여 있다. ESV가 더 빼는 마 12:47도 `[ ]`로 묶여 있다
- 표본 밖에서 다른 생략이나 병합이 있을 수 있다. 전권 수치는 적재 후 확정한다(9절)

## 5. 현재 코드로 받으면 생기는 문제

### 5.1 요나: `jon` 코드는 빈 페이지다

`bible.list.js`의 책 목록을 보면 bskorea는 7개 역본(`HAN`, `GAE`, `SAE`, `SAENEW`, `COG`, `COGNEW`, `CEV`) 모두 요나를 **`jnh`**로 쓴다. 저장소의 `USFM_BOOK_CODES`는 `jon`이다(eBible은 `JON`이 맞다). 나머지 65권의 코드와 장 수는 `SAENEW`·`GAE` 모두 저장소 상수와 같다.

- `book=jon` 요청은 **200 응답에 본문 없는 페이지**를 돌려준다. 새번역과 개역개정 둘 다 그렇다(2026-10-29 실측). `jnh`는 정상이다
- bskorea 파서는 `[]`를 돌려주고, 체인이 범용 파서로 넘어간다. 범용 파서는 페이지의 입력 폼 문구를 읽어 **1절짜리 장**을 만든다. 첫 절 번호가 1이고 본문이 비어 있지 않으므로 적재기의 빈 장 가드를 그대로 통과한다. 요나 4개 장에 쓰레기 절이 하나씩 들어간다
- `resolve_book_code_for_source()`는 bskorea에서 `bible_book.book_key`(`JON`)를 우선하므로, 상수만 고쳐서는 안 고쳐진다(6.3)
- 참고: DB의 NKRV 요나 48절은 정상 길이의 본문이다. 다만 1:1만 처음 적재 순서의 id(87008)이고 나머지 47절은 한참 뒤의 id(87577–87623)다. 오바댜의 마지막 절(87007)과 미가의 첫 절(87012) 사이에 요나 몫은 4개, 곧 장마다 1개뿐이다. 처음 적재가 위 동작대로 장마다 1절씩 넣었고 나중에 보정된 것으로 보이지만, 기록은 없다(추정)

### 5.2 시편 표제 `<H VAL=1.1>`이 장 전체를 감싼다

새번역의 표제 시편은 표제를 닫는 태그 없는 `<H VAL=1.1>`로 시작한다.

```html
<div id="tdBible1" class="bible_read">
  ... <font class="smallTitle">(소제목)</font><br />
  <H VAL=1.1>(표제)<br/><br/>
  <span><span class="number">1&nbsp;&nbsp;&nbsp;</span>(본문)</span><br />
  ...   <!-- </H> 없음: html.parser가 장 끝까지 전부 H의 자식으로 넣는다 -->
</div>
```

- 현재 파서는 루트의 **직계** `span`만 보므로 절을 하나도 찾지 못하고 `[]`를 돌려준다. 체인은 `_extract_verses_from_structured_nodes()`로 넘어간다
- 범용 파서는 절 수는 맞췄다(시 3편 8절, 18편 50절, 51편 19절). 표제도 1절에 들어가지 않았다. 대신 **각주 번호(`1)`)와 숨김 각주 본문이 절에 섞이고**(시 3:2, 3:3, 18:2, 18:5, 18:13, 18:29), 공백이 달라졌다(시 3:4, 3:8, 18:10, 18:50, 51:18). 절 수 검사로는 찾을 수 없다
- 개역개정 시 3편과 92편에는 이 태그가 없다. 새번역에서만 나온다. 표본의 표제 시편 3편이 모두 이 구조였고, 표제가 없는 119·150편은 아니었다

### 5.3 절 중간 소제목

단락이 절 중간에서 나뉘는 곳은 소제목이 **절 `span` 안에** 있다. 6곳: 삼하 19:8, 19:18, 19:40, 미 5:5, 눅 23:56, 행 8:1.

```html
<span><span class="number">8&nbsp;&nbsp;&nbsp;</span>(본문 앞부분)<br /><br /><br />
  <font class="smallTitle">(소제목)</font><br />(본문 뒷부분)</span>
```

현재 파서는 `font.smallTitle`을 지우지 않으므로 소제목이 본문에 들어간다. 눅 23:56의 소제목은 평행 본문 참조(`<a TAR=…>마 28:1-10</a>` 등)까지 달고 있어, 숫자와 참조가 본문에 섞인다. BibleGateway의 `h4` 화자 표시가 절 중간에 들어가던 문제(NIV 설계 문서)와 같은 종류다.

### 5.4 절 안 줄바꿈 `<br>`

한 절 안에서 문단이 바뀌는 곳은 `…(문장 끝).<br /><font size='1'></font>(다음 문장)`처럼 **공백 없이** `<br>`만 있다. `get_text("")`는 `<br>`를 빈 문자열로 읽으므로 앞 문장의 마침표와 다음 단어가 붙는다. 표본에서 17절이다(출 22:29, 레 6:9, 6:25, 민 16:19, 16:27, 삼상 24:7, 왕상 4:2, 4:8, 4:19, 대상 6:3, 6:71, 6:77, 겔 21:24, 단 4:1, 4:19, 6:25, 요 5:9). 정규식 `[.?!]["'”’]?[가-힣]`이 정확히 이 17절을 찾는다.

### 5.5 생략 절 표지 `(21절 없음)`

새번역은 생략한 절에 `span`을 만들지 않고, **앞 절 `span` 끝에 표지를 붙인다.** 각주(`a.comment` + `div.D2`)는 어떤 사본에 그 절이 있는지 설명한다.

```html
<span><span class="number">20&nbsp;&nbsp;&nbsp;</span>(본문) <a class=comment>4)</a>(21절 없음)
  <div class=D2 style='display:none'>(각주)</div></span>
```

- 표본의 표지 14개가 모두 이 위치(앞 절 본문의 맨 끝)다. 형식은 두 가지다: `(N절 없음)` 13개, `(6절 하반부터 8절 상반까지 없음)` 1개(행 24:6). 뒤의 것은 24:7 전체와 24:6·24:8의 일부가 없다는 뜻이다
- 현재 파서는 표지를 본문으로 읽어 **앞 절 끝에 저장한다.** 생략된 절은 구멍이 된다
- 표지와 구멍은 표본에서 정확히 일대일이다. 구멍 14개 모두 표지가 있고, 표지 14개 모두 구멍을 가리킨다

이 절들을 어떻게 저장할지는 12절의 결정 항목이다. 판단 근거는 두 가지다.

- 저장소 규칙은 "페이지에 근거가 있으면 자리표시 행, 없으면 구멍"이다. WEB·SBLM은 각주만 있는 빈 `span`이 근거라 `(omitted)`를 넣고, ASV·ESV·N1904는 근거가 없어 구멍으로 둔다. 새번역은 페이지가 절 번호를 직접 밝히므로(`(21절 없음)`) **자리표시 행이 이 규칙에 맞다**
- **DB의 한국어 역본은 이미 `(없음)` 행을 쓴다.** 개역개정 페이지는 생략 절을 자기 `span`에 `(없음)`으로 싣고, 현재 파서가 그대로 저장했다. NKRV(2)의 생략 좌표는 **새번역 표본의 14절과 정확히 같은 14곳**이고, 12곳이 `(없음)`이다(나머지 둘은 7절). 개역한글(1)도 13곳이 `(없음)`이다

따라서 새번역도 표지가 가리킨 번호에 **`(없음)` 행**을 넣는 것을 권장한다. 한국어 역본끼리 같은 좌표에 같은 문자열이 놓여 병렬 표시가 맞는다. 영어 자리표시 `(omitted)`를 쓰면 저장소 전체에서 한 문자열로 찾을 수 있지만, 같은 DB의 NKRV·KRV와 어긋난다.

### 5.6 아가 화자 표기

새번역 아가는 화자를 `(여자)`, `(남자)`, `(친구들)`로 표시한다. 마크업 없는 **일반 텍스트**이고, 위치는 세 가지다.

- 절 끝: 다음 절부터 말하는 사람을 앞 절 끝에 붙인다(13개)
- 절 중간: 한 절 안에서 화자가 바뀌는 곳(3개: 아 1:4, 6:13, 7:9)
- 장 첫머리: 절 밖 루트 텍스트(아 6·7장의 `(친구들)`). 지금도 절에 들어가지 않는다

표본 3개 장에서 절 안에 16개다(`(여자)` 6, `(남자)` 6, `(친구들)` 4). 저장소는 BibleGateway의 `h4.speaker`(WEB·NIV 아가 화자 표시)를 지운다. 새번역의 표기는 마크업이 아니라서 텍스트로 지워야 한다. 그리고 다음 절의 화자를 앞 절에 붙여 두므로, 그대로 저장하면 **화자가 틀린 절에 붙는다.** 지우는 쪽을 권장한다(12절).

### 5.7 병합 절 번호 `18-19` (개역개정에서 확인)

개역개정 페이지에는 `span.number`가 `18-19`(신 6장), `1-3`(시 92편)인 절이 있다. 현재 파서는 첫 숫자만 읽어 18, 1에 저장하고 **19, 2, 3을 잃는다.** DB의 NKRV는 KJV보다 13개 좌표가 모자라는데(신 6:19, 15:5, 30:10, 대상 16:13, 시 92:2, 92:3, 105:6, 렘 32:4, 32:5, 33:11, 겔 24:5, 행 15:26, 롬 9:2), **13개 모두 이 경우다.** 처음에는 두 장(좌표 3개)만 확인했고, 2026-10-30에 나머지 9개 장을 받아 13개 좌표가 모두 오늘 페이지의 범위 번호 안에 있음을 확인했다(`18-19`, `4-5`, `9-10`, `12-13`, `1-3`, `5-6`, `3-5`, `10-11`, `4-5`, `25-26`, `1-2`).

새번역 표본 2,100절에는 범위 번호가 없다. 하지만 표본 밖에 있을 수 있으므로 파서가 처리해야 한다. 저장소 규칙(jpn.bible, wikisource)대로 **범위가 덮는 모든 번호에 같은 본문을 저장한다.** 절 번호 연속성이 유지되고 어느 번호로 찾아도 본문이 나온다.

### 5.8 그대로 두는 것

- `(셀라)` — 시편 본문의 일부다(표본 시 3편에 3개). NIV·ESV의 `Selah`도 남겼다
- `[ ]` — 사본 근거가 약한 본문을 묶는 원문 기호다(마 12:47, 막 16:9–20, 요 5:3–4, 요 7:53–8:11, 롬 16:25–27 등). ESV의 `[[ ]]`와 같이 그대로 둔다
- 번역자의 괄호 설명(막 7:11, 7:34 등 8곳) — 본문의 일부다
- 루트의 `font.smallTitle`, 숨김 책명, 장 번호, 역본명 — 절 밖이라 지금도 들어가지 않는다

## 6. 코드 변경 설계

### 6.1 배선 (`scrape_bible_to_db.py`)

ESV 때와 같은 네 곳이다. 타입 이름은 DB의 `translation_type`(`RNKSV`)과 같아야 한다.

```python
ENTRY_URL_ENV_BY_TRANSLATION_TYPE["RNKSV"] = "RNKSV_ENTRY_URL"
TRANSLATION_TYPES_BY_LANGUAGE_CODE["ko"] = ("NKRV", "RNKSV")
ENTRY_URL_PREFERENCE_ORDER = (..., "ESV", "RNKSV")   # NKRV가 맨 앞이라 기존 기본값은 그대로
TRANSLATION_SOURCE_REQUIREMENTS["RNKSV"] = {
    # Same source as NKRV; only the version token tells the two apart. bskorea also
    # serves SAE (표준새번역 1993), a separate edition the exact match keeps out.
    "source": "bskorea",
    "version": "SAENEW",
    "name": "새번역",
    "language_code": "ko",
}
```

- `ko`가 두 역본을 가리키게 되므로, `.env`에 `NKRV_ENTRY_URL`과 `RNKSV_ENTRY_URL`이 같이 있으면 `BIBLE_LANGUAGE_CODE=ko`만으로는 엔트리가 정해지지 않고 중단된다. `en`·`es`·`ja`·`zh`와 같은 동작이다. `BIBLE_TRANSLATION_TYPE`이나 `--entry-url`을 준다
- `LEGACY_TRANSLATION_TYPE_BY_ID`(`2 → NKRV`)와 이름 힌트(`개역개정 → NKRV`)는 그대로 둔다

### 6.2 `get_source_version()` — 기본값 `GAE`를 보고한다

`_build_bskorea_url()`은 엔트리 URL에 `version`이 없으면 `GAE`를 쓴다. 그런데 `get_source_version()`은 그 경우 `None`을 돌려준다. `RNKSV` 행을 추가하면 다음 구멍이 생긴다.

- `RNKSV_ENTRY_URL`에 `version=`을 빠뜨린다 → 버전 `None` → 기대 타입 없음 → 두 번째 분기에서 `RNKSV`의 소스가 bskorea로 일치하고, 버전이 `None`이라 버전 검사를 건너뛴다 → **통과한다.** 실제로는 개역개정 본문을 받아 새번역 행에 넣는다

bskorea는 `get_source_version()`이 빌더와 같은 기본값을 보고하도록 한다(`query.get("version", "GAE")`). 그러면 위 경우는 기대 타입이 `NKRV`가 되어 `RNKSV` 메타데이터와 어긋나므로 중단된다. 버전 없는 URL로 NKRV를 받는 기존 동작은 기대 타입이 `NKRV`로 정해질 뿐 그대로 통과한다. BibleGateway도 같은 모양(기본값 `WEB`)이지만 이번 범위 밖이다.

### 6.3 책 코드 — 요나 `jnh`

- bskorea 전용 예외표를 둔다: `BSKOREA_BOOK_CODE_OVERRIDES = {"jon": "jnh"}`. `USFM_BOOK_CODES`는 eBible과 공유하므로 바꾸지 않는다
- `_get_bskorea_book_code()`와 `resolve_book_code_for_source()`의 bskorea 분기 **둘 다** 결과에 이 표를 적용한다. `book_key`를 우선하는 현재 동작과 기존 테스트(`WRONG` → `wrong`)는 그대로 둔다. `book_key`가 `JON`이어도 `jnh`가 된다
- 근거는 `bible.list.js`다(5.1). 코드 주석에 이 출처와 확인 날짜를 남긴다

### 6.4 파서 (`_extract_verses_from_bskorea_read_page`)

| 변경 | 이유 |
| --- | --- |
| 절 `span`을 **재귀로** 찾는다. 기준은 "직계 자식으로 `span.number`를 가진 `span`"이고, 다른 절 `span` 안에 있는 것은 건너뛴다 | `<H VAL=1.1>` 안의 절(5.2). 표제 텍스트는 어느 절 `span`에도 속하지 않으므로 자동으로 빠진다 |
| 제거 목록에 `font.smallTitle` 추가 | 절 중간 소제목과 그 평행 본문 참조(5.3) |
| `get_text("")` 전에 `<br>`를 공백 하나로 바꾼다 | 문장 붙음(5.4). `<br>`는 단어 안에 오지 않으므로 조사가 갈라지지 않는다 |
| 번호를 `^(\d{1,3})(?:-(\d{1,3}))?$`로 읽고, 범위면 덮는 모든 번호에 저장한다. 다른 형식이면 그 장은 `[]`와 경고 | 병합 절(5.7). 모르는 형식을 추측하지 않는다 |
| 절 본문 끝의 `(N절 없음)`, `(A절 하반부터 B절 상반까지 없음)`을 떼어 내고, 가리키는 절 번호를 모은다. 끝에 `없음)`이 있는데 두 형식이 아니면 그 장은 `[]`와 경고 | 생략 표지(5.5) |
| 장 단위 자기 검사: 절 번호 구멍과 표지가 가리키는 번호가 **정확히 같아야** 한다. 표지가 가리키는 번호에 `span`이 따로 있어도 실패 | 표지 없는 구멍은 파싱 실패이고, 표지만 있고 구멍이 없으면 해석이 틀린 것이다 |
| 표지가 가리키는 번호는 12절의 결정대로 자리표시 행으로 넣거나 구멍으로 둔다. 자리표시는 새 상수(예: `BSKOREA_OMITTED_VERSE_TEXT = "(없음)"`)로 두고, 표지가 있을 때만 만든다 | 권장은 `(없음)` 행(5.5) |

각주(`a.comment`, `div.D2`)와 숨김 노드 제거, 인라인 `font` 보존, `get_text("")`, `#tdBible1` 우선은 바꾸지 않는다.

### 6.5 bskorea 페이지는 범용 파서로 넘기지 않는다

`_extract_verses()`에서 소스가 bskorea이면 bskorea 파서의 결과를 **비어 있어도 그대로** 돌려준다. 체인을 계속 내려가지 않는다.

- 5.1(빈 페이지 → 1절짜리 쓰레기 장)과 5.2(표제 시편 → 각주 섞인 본문)는 둘 다 범용 파서가 만든 결과다. 둘 다 적재기의 가드를 통과했다
- 빈 결과는 적재기가 그 장을 쓰기 전에 건너뛰고, 책 전체가 비면 예외를 낸다. 실패가 드러나는 쪽이 맞다
- CLAUDE.md의 "소스 전용 파서는 자기 소스가 아닐 때 `[]`를 돌려 체인을 잇는다"는 규칙과 어긋나지 않는다. 여기서는 소스가 bskorea임을 URL로 이미 안다. 다른 소스에도 같은 문제가 있을 수 있지만 이번 범위 밖이다

### 6.6 아가 화자 표기 제거 — 책 번호를 아는 곳에서

파서는 `soup`만 받고 책 번호를 모른다. 적재(`process_book`), smoke test, 드리프트 점검(`check_translation_drift.py`)이 모두 `fetch_chapter_payload(book_order, …)`를 거치므로 여기서 처리한다.

- 소스가 bskorea이고 `book_order == 22`일 때만, 절 본문에서 `\((여자|남자|친구들)\)`를 지우고 공백을 정리한다
- 목록에 없는 괄호 표기가 아가에 남는지는 적재 후 검증한다(9절). 늘릴 때는 실측으로만 늘린다
- 표기를 지워 빈 절이 생기면 그 장을 건너뛴다(경고). 이 단계는 파서의 구멍 검사 뒤에 돌므로, 그냥 두면 빈 절이 정리 단계에서 빠지고 아무도 모르는 구멍이 남는다(15.6)
- DB의 NKRV·개역한글에는 이 세 표기가 어느 책에도 없다(2026-10-29 조회). 개역개정에는 영향이 없다

### 6.7 시제품 실측

6.4~6.5를 저장소 밖의 시제품으로 짜서 표본 전체에 돌렸다(아가 표기 제거는 넣지 않았다).

| 바뀐 절 | 개수 | 위치 |
| --- | --- | --- |
| `<br>` 자리에 공백 | 17 | 5.4 목록 |
| 절 중간 소제목 제거 | 6 | 5.3 목록 |
| 생략 표지 제거 | 14 | 5.5 (앞 절) |
| 표제 시편: 각주·공백 정리 | 11 | 5.2 목록 |
| **합계** | **48** / 2,100 | 위 넷 밖의 변화 없음 |

- 시제품 결과에는 각주 번호 `N)`, 끝의 `없음)`, 문장 붙음(5.4의 정규식)이 **0**이다. 남은 괄호는 아가 화자 표기(5.6)와 5.8의 원문 괄호뿐이다
- 생략 표지 14개와 구멍 14개가 장마다 정확히 맞아 자기 검사를 통과한다
- 요나 1장(`jnh`)은 17절, 표지 없음이다

## 7. 개역개정(NKRV)에 미치는 영향

6.3~6.5는 bskorea 공용 코드라 개역개정에도 적용된다. `GAE` 15개 장으로 확인했다(2026-10-29에 6개, 2026-10-30에 9개). 새 파서는 15개 장을 하나도 거부하지 않았다.

- 시제품 결과가 현재 파서와 다른 곳은 **삼하 19:8과 행 8:1 두 곳**이다. 오늘의 `GAE` 페이지도 이 두 절에 절 중간 소제목이 있어, 현재 파서로는 소제목이 섞인다. **DB의 NKRV에는 섞여 있지 않다**(행 8:1은 시제품 결과와 같다). 적재 당시 페이지 구조가 달랐던 것으로 보인다
- 확인한 15개 장에서, 병합 절로 새로 생기는 13개 좌표를 빼면 오늘의 `GAE` 페이지는 적재된 NKRV와 두 곳이 다르다: 삼하 19:8의 마침표 하나, 행 8:37(DB는 `없음`, 페이지는 `(없음)`). **대한성서공회는 게시 본문을 고친다.** 새번역도 적재본이 낡을 수 있다(리스크 5)
- NKRV의 생략 14곳 중 두 곳은 `(없음)`과 글자가 다르다: 행 8:37 `없음`(위), 행 24:7 `（없음）`(전각 괄호). 새번역을 `(없음)`으로 넣으면 이 두 곳만 NKRV와 어긋난다. NKRV를 고칠지는 별도 결정이다
- 병합 절(5.7)을 처리하면 NKRV 장을 다시 돌릴 때 빠진 13개 좌표가 **새로 들어간다**(missing-only insert는 없는 절을 채운다). 이건 데이터 쓰기이므로 사용자가 요청할 때만 한다. 이미 있는 절은 고쳐지지 않는다
- 문장 붙음 정규식(5.4)은 DB의 NKRV·개역한글에서 0건이고, `GAE` 6개 장에서도 `<br>` 변경으로 바뀐 절이 없었다. NKRV에는 5.4의 문제가 나타나지 않는다
- `check_translation_drift.py --translation-id 2`는 같은 어댑터로 다시 파싱하므로, 파서를 바꾸면 위 차이가 드리프트로 보고된다. 파서 변경 후 NKRV 드리프트를 한 번 돌려 차이가 이 절의 목록뿐인지 확인한다

## 8. DB 준비

현재 상태(2026-10-29 실측, 읽기 전용 조회):

| 항목 | 상태 |
| --- | --- |
| `bible_translation` | **id 3, `RNKSV`, `새번역`, `ko`, `translation_order` 3 행이 이미 있다.** `attribution`은 NULL |
| `translation_type` CHECK | `RNKSV` **이미 포함** |
| `bible_book` / `bible_chapter` / `bible_verse` | 0 / 0 / 0 |
| `bible_book` 최대 id | 1044. identity는 `BY DEFAULT` |

DDL은 필요 없다. `bible_book` 66행은 개역개정(2) 행을 복사한다.

```sql
SELECT setval('public.bible_book_id_seq', (SELECT COALESCE(MAX(id), 0) FROM public.bible_book), true);

INSERT INTO public.bible_book
    (translation_id, book_order, book_key, name, abbreviation, testament_type)
SELECT 3, src.book_order, src.book_key, src.name, src.abbreviation, src.testament_type
FROM public.bible_book src
WHERE src.translation_id = 2
  AND NOT EXISTS (
      SELECT 1 FROM public.bible_book dst
      WHERE dst.translation_id = 3 AND dst.book_order = src.book_order
  )
ORDER BY src.book_order;

UPDATE public.bible_translation
SET attribution = '성경전서 새번역 © 대한성서공회'
WHERE id = 3 AND attribution IS NULL;
```

- 이 SQL은 도구 밖에서, 사용자가 요청할 때만 실행한다. 도구는 `bible_book`을 만들지 않는다
- `setval`은 ESV 때와 같은 이유다. `bible_book`의 identity가 `BY DEFAULT`라 시퀀스가 `MAX(id)`보다 뒤처져 있을 수 있다
- `book_key`는 NKRV와 같은 USFM 대문자 코드다. 요나는 `JON`이고, URL에서는 6.3의 예외표가 `jnh`로 바꾼다
- **책 이름**: 새번역의 공식 책 이름은 31권이 개역개정과 다르다(`bible.list.js` 기준). 예: 여호수아기, 사무엘기상, 역대지상, 에스라기, 이사야서, 요나서, 마태복음서, 요한1서. 위 SQL은 앱에서 한국어 역본끼리 이름이 같도록 개역개정 이름을 복사한다. 새번역 이름을 쓸지는 12절의 결정 항목이다
- 트랜잭션 풀러(6543) 환경이므로 세션 단위 `SET`을 쓰지 않는다(CLAUDE.md)

## 13. 리스크

### 리스크 1. 새번역 본문이 개역개정 행으로, 또는 그 반대로 들어간다

같은 소스라 `version`만이 둘을 가른다. 대응: 6.1의 행, 6.2의 기본값 보고, 양방향 거부 테스트.

### 리스크 2. 범용 파서가 만든 그럴듯한 결과가 통과한다

5.1과 5.2가 실제 예다. 5.2는 절 수와 연속성 검사를 모두 통과했다. 5.1은 적재기의 가드를 통과하고, 적재 뒤 KJV 절 수 대조에서야 드러난다. 대응: 6.5로 bskorea 페이지를 범용 파서에 넘기지 않고, 9절의 오염 쿼리를 돌린다.

### 리스크 3. 표본 밖의 구조

표본은 67개 장(5.6%)이다. 다른 표지 형식, 다른 위치의 `<H>`, 범위 번호가 더 있을 수 있다. 대응: 6.4는 모르는 형식을 추측하지 않고 그 장을 비운다. 비워진 장은 로그와 9절의 장 수 검증에서 드러난다. 그때 원문을 보고 규칙을 넓힌다.

### 리스크 4. 권리 상태를 잊는다

대응: README·CLAUDE.md에 새번역의 권리 상태를 적고, 적재하면 `attribution`을 비워 두지 않는다.

### 리스크 5. 적재본이 낡는다

대한성서공회는 게시 본문을 고친다(7절, NKRV 두 곳). missing-only라 다시 돌려도 고쳐지지 않는다. 대응: `check_translation_drift.py`로 차이를 찾고, 절 → 장 순서로 지운 뒤 다시 적재한다.

## 14. 결론

새번역은 개역개정과 같은 소스·같은 URL 규칙이라 배선은 한 행이면 된다. 그러나 표본에서 **현재 bskorea 파서와 책 코드의 결함 다섯 가지**(요나 코드, 시편 표제 래퍼, 절 중간 소제목, 절 안 줄바꿈, 생략 표지)가 나왔고, 모두 적재기의 가드를 통과하는 종류였다. 개역개정에서는 병합 절 번호로 13개 좌표가 빠진 원인도 찾았다. 파서 변경(6.4~6.5)을 시제품으로 표본에 돌린 결과, 결함 위치 48절만 바뀌고 나머지는 그대로였다. 남은 순서는 DB 준비 → (권리 게이트를 통과하면) 적재 → 9절 검증이다. 12절의 결정, 코드 변경과 테스트, smoke test는 끝났다(15절).

### 15.2 테스트
