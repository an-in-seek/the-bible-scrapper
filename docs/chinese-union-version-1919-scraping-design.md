# 和合本(1919) 중국어 성경 본문 스크래핑 개발 설계

## 1. 목적

1919년 『聖經和合本』(Chinese Union Version) 66권을 **번체·간체 두 벌**로 스크래핑하여 기존 PostgreSQL 스키마(`bible_chapter`, `bible_verse`)에 적재한다.

### 1.1 제시된 근거 검토

요청과 함께 제시된 내용은 이렇다.

> 가장 안전한 기본 판본: **1919년 화합본(CUV)** — 간체/번체 모두 Public Domain 자료가 존재.
> 단, 인터넷에서 구한 아무 CUV 파일이나 쓰면 안 되고 **Public Domain 출처가 명확한 데이터셋**을 사용해야 합니다.

**실측 결과 이 판단은 맞고, 마지막 문장이 특히 맞다.** 중국어 성경 소스를 조사하면 가장 먼저 눈에 띄는 것이 eBible.org의 `cmn-cu89s`/`cmn-cu89t`이고, 이 저장소에는 이미 eBible 어댑터가 있어 **비용이 거의 0**이다. 그런데 그 텍스트는 **1919년판이 아니다**([1.3](#13-ebible의-중국어-화합본은-1919년판이-아니다)).

### 1.2 판본 계보 — 무엇이 퍼블릭 도메인인가

| 판본 | 발행 | 상태 (조회 결과) |
| --- | --- | --- |
| **『聖經和合本』(國語和合譯本)** | **1919** | 퍼블릭 도메인. 維基文庫 표기: 「此作品在全世界都屬於公有領域，因為作者逝世已經超過100年，且作品於1931年1月1日之前出版」 |
| 『新標點和合本』(CUNP) | 1988, 聯合聖經公會 | **분쟁 소지.** eBible은 `Public Domain`으로 표기하지만, 홍콩 교계 문헌은 보호 대상이라고 적는다(아래) |

홍콩교회갱신운동 총간사가 쓴 2015-12-18 기고문은 두 판본을 나란히 놓고 이렇게 구분한다.

```
《聖經和合本》(1919年)，其版權滿了50年，已成為「公版」(public domain)，任何人使用而毋須申請版權。
《新標點和合本》於1988年出版，其中涉及標點、分段、地名等修訂，而《新標點和合本》則受版權條例保護。
```

中文 위키백과의 『新標點和合本』 항목도 1988년 聯合聖經公會 발행이며 **구두점·분단·인명·지명을 고쳤다**고 적는다(용어와 문체는 기본적으로 바꾸지 않았다고 명시).

> **1919년판은 관할을 가리지 않고 깨끗하다.** 1931년 이전 발행이라 미국에서도 URAA 복원 대상이 아니다. 직전 일본어 작업([口語訳 설계](japanese-colloquial-1955-scraping-design.md) 1.2)에서 문제가 됐던 "일본은 만료, 미국은 존속" 같은 상황이 여기서는 생기지 않는다.
>
> 이 문서는 법률 자문이 아니다. 위는 배포처·위키·교계 문헌의 표기를 조회한 결과이며 판단은 사용자 몫이다.

### 1.3 eBible의 중국어 화합본은 1919년판이 아니다

eBible.org `translations.csv`(731 KB, 전량 조회)의 `cmn` 행은 8개이고, 그중 화합본 계열은 둘이다.

| ID | 제목 | 배포 표기 | 구약 | 신약 |
| --- | --- | --- | --- | --- |
| `cmn-cu89s` | 新标点和合本 | `public domain` | 39권/929장/23,081절 | 27권/260장/7,940절 |
| `cmn-cu89t` | 新標點和合本 | `public domain` | 39권/929장/23,081절 | 27권/260장/7,940절 |

**제목이 이미 답이다 — 新標點和合本, 즉 1988년판이다.** ID의 `cu89`도 1989를 가리킨다. 위키백과가 열거한 개정 항목을 그대로 지표로 삼아 확인했다.

| 확인 절 | 1919년판 | eBible `cmn-cu89s` 실측 |
| --- | --- | --- |
| 창 2:14 | 伯拉河 | **幼发拉底河** |
| 창 29:32 | 流便 | **吕便** |
| 창 14:15 | 大馬色 | **大马士革** |

세 곳 모두 개정판 쪽이다. 구두점도 다르다.

```
1919      起初　神創造天地。          ← 敬空(U+3000) + 구식 구두점 ．、
cu89s     起初，神创造天地。          ← 현대 구두점, 敬空 없음
```

**두 eBible 판은 자형만 다른 것도 아니다.** 간체는 神판, 번체는 上帝판이다.

```
cmn-cu89s  起初，神创造天地。
cmn-cu89t  起初，上帝創造天地。
```

즉 eBible을 쓰면 (가) 1919년판이 아니고, (나) 배포처 표기와 홍콩 교계 문헌이 어긋나며, (다) 간체·번체가 신명 표기까지 다른 서로 다른 판이 된다. **요청이 "1919년판, 퍼블릭 도메인 출처가 명확한 것"이므로 채택하지 않는다.**

공정을 기하면, eBible 페이지 자체도 `div.copyright`에 `Public Domain`을 싣고 있고 배포처는 재배포 가능(`Redistributable=True`)으로 분류한다. 다투는 것은 **1988년 개정분의 권리**이지 eBible의 성실성이 아니다.

維基文庫를 고른 이유는 셋이다.

1. **판본이 1919년판임을 실측으로 확인했다.** 伯拉河·流便·大馬色·구식 구두점·敬空이 모두 원판 쪽이다.
2. **권리 근거가 문서에 붙어 있다.** 1931년 이전 발행 + 저자 사후 100년이라는, 관할을 가리지 않는 가장 강한 근거다.
3. **한 소스에서 번체·간체가 모두 나온다.** MediaWiki의 자형 변환을 쓰므로 `/zh-hant/`와 `/zh-hans/`가 같은 원문에서 생성된다. 창세기로 확인한 결과 **장·절 구조가 완전히 동일**하다(50장 1,533절).

## 2. 결론 먼저

1. **새 소스 어댑터가 필요하다.** 기존 eBible 어댑터는 1988년판만 서비스하므로 재사용할 수 없다.
2. **URL 규칙이 책 단위다.** `https://zh.wikisource.org/zh-hant/聖經_(和合本)/創世記` 한 페이지에 창세기 50장이 모두 있다. **직전 jpn.bible 작업에서 만든 책 페이지 캐시 구조를 그대로 재사용한다**([5.1](#51-scraperpy--책-페이지-캐시-재사용)). 전권 요청 수는 역본당 **66회**다.
3. **번체·간체는 URL 접두어만 다르다.** `/zh-hant/`와 `/zh-hans/`. 어댑터는 하나, 엔트리 URL은 둘, 역본은 둘(`CUVT`/`CUVS`)이다.
4. **절 총계는 31,102절이고 KJV 총계와 같은데, 장별로는 4개 장이 다르다.** 차이가 +1 −1 −1 +1로 상쇄되어 총계가 우연히 맞는 것이므로 **총계만 보고 판단하면 안 된다**([7.4](#74-kjv-대조--네-개-장)). 장 수는 66권 모두 `KJV_CHAPTER_COUNTS`와 일치하고 연속성이 깨진 장은 **0개**다.
5. **파서 함정이 일곱이다.** 한 문단에 절 마커가 여럿 붙는 병합 표기(69건), 한자 숫자 장 제목과 시편의 `詩篇卷N` 절 구분 제목, **敬空(U+3000)**, 절 안에 섞인 **숫자 아닌 `sup`**(상호참조 289건), 본문에 포함되는 **소자주**(998절), 1절에 녹아 있는 **시편 표제**(116편), 그리고 책 끝의 **라이선스 상자**다([4.3](#43-함정-1-한-문단에-마커가-여럿-붙는다)~[4.9](#49-마지막-장-뒤에-라이선스-상자가-있다)).
6. **敬空은 현재 파이프라인에서 사라진다.** 전체의 **11.4%(3,557절)**가 神·主 앞에 U+3000을 갖고 있는데, `_normalize_text`가 보통 공백으로 접고 `CJK_JOIN_PATTERN`이 지운다. 낱말은 그대로이고 조판 관행만 사라지는 것이라 **그대로 두기를 권고**하되, 이것이 선택임을 문서에 남긴다.
7. **DB 작업이 지금까지 중 가장 많다.** 역본이 둘이라 CHECK 값 2개, `bible_translation` 2행, `bible_book` **132행**이 필요하고, `bible_book_description`의 `zh` **66행이 신규**다.

### 3.1 확인하지 못한 것

1. ~~아직 구현하지 않았다.~~ **구현·적재를 마쳤다**([12.5](#125-적재-결과-실측)). 이 절의 수치는 프로토타입에서 나왔지만 이후 저장소 코드 경로로 전권을 돌려 같은 값이 나오는 것을 확인했다.

## 4. 대상 페이지 특성

### 4.1 URL 규칙 — 책 단위, 자형은 접두어

```
https://zh.wikisource.org/zh-hant/聖經_(和合本)/{책이름}      # 번체
https://zh.wikisource.org/zh-hans/聖經_(和合本)/{책이름}      # 간체
```

- 색인 페이지 `聖經_(和合本)`에서 **책 페이지 66개**를 얻었다(canonical 순서: 創世記 … 啟示錄).
- 책 이름은 번체 표기 그대로 쓴다. `/zh-hans/`로 요청해도 **경로의 책 이름은 번체**이며 본문만 변환되어 온다(창세기로 확인).
- 장 단위 URL은 없다. 장은 문서 안의 `h2` 제목이며(전권에 `h3`은 **0개**), **1,189개 모두 `id`가 제목 텍스트와 같다**(`id="第一章"`). 사람이 볼 때는 `#第一章`으로 가리킬 수 있다.
- 다만 **어댑터가 만드는 프래그먼트는 아라비아 숫자**(`#3`)다. 한자 숫자 표기가 불규칙해서 정수에서 생성할 수 없기 때문이다 — 실측하면 110은 `一百一十`인데 111은 `一百十一`, 119는 `一百十九`로 십의 자리 `一`이 빠진다. 프래그먼트는 페이지 앵커가 아니라 **캐시에서 장을 고르는 내부 키**로만 쓴다.
- 페이지 크기는 창세기 기준 약 385 KB.

### 4.2 DOM 구조

본문 루트는 `div.mw-parser-output`이고, 그 안은 단순하다.

```html
<div class="mw-heading mw-heading2"><h2 id="第一章">第一章</h2>…</div>
<p><sup>1</sup>起初　神創造天地。</p>
<p><sup>2</sup>地是空虛混沌．淵面黑暗．　神的靈運行在水面上。</p>
…
<p><sup>29</sup><sup>30</sup>利百加有一個哥哥、名叫拉班、…</p>   ← 병합 표기
```

| 요소 | 개수(전권) | 역할 |
| --- | ---: | --- |
| `h2` | 1,194 | 장 제목 (`第一章`, 시편은 `第一篇`). **전부 `id`를 갖는다** |
| `p` | 31,361 | 문단. 절 문단 외에 머리말·라이선스 문단도 포함한 수다 |
| `sup` (p 안, 숫자) | 31,102 | 절 마커. **한 문단에 여럿 올 수 있다** |
| `sup` (p 안, 숫자 아님) | 289 | **상호참조 마커.** 蘇州숫자(〡〢〣…)이며 절 번호가 아니다 |
| `sup` (dd 안) | 289 | 상호참조 각주 본체의 마커 |
| `dl` / `dd` | 112 / 289 | **상호참조 각주.** 장 끝에 모여 있다 |
| `small` | 1,211 | **소자주(小字註).** 절 본문 안에 있다 |
| `span.mw-editsection` | — | 「編輯」 링크 — 제거 대상 |
| `table` | — | 목차·라이선스 표 — 제거 대상 |

**각주와 상호참조가 있다.** `h2` 1,194개는 1,189장 + [4.4](#44-함정-2-장-제목이-한자-숫자이고-시편에는-장이-아닌-제목이-섞인다)의 `詩篇卷N` 5개다.

### 4.3 함정 1. 한 문단에 마커가 여럿 붙는다

원문이 두 절 이상을 한 단위로 조판한 곳에서 `sup`가 연달아 나온다.

```html
<p><sup>29</sup><sup>30</sup>利百加有一個哥哥、…</p>     창 24:29-30
```

**첫 `sup`만 읽으면 뒤 번호가 통째로 사라진다.** 프로토타입 1차 구현이 정확히 그랬고, 창세기가 1,532절(1절 부족)로 나와 드러났다. 전권 조사 결과 **69건**이며 추가 번호는 70개다(폭 3짜리가 하나 — 시 8:6-8).

저장 방식은 [口語訳 설계 §4.4](japanese-colloquial-1955-scraping-design.md)·[jpn1965 설계 §4.4](new-japanese-nt-scraping-design.md)와 **같은 결정**이다. **결정: B안 — 범위의 모든 번호에 같은 본문을 저장.** 절 번호 연속이라는 불변식을 지키면서 어떤 번호로 조회해도 올바른 본문이 나온다.

> B안이면 총 절 수가 **31,102**이고, 앞 번호에만 저장하는 A안이면 31,032이다.

### 4.4 함정 2. 장 제목이 한자 숫자이고, 시편에는 장이 아닌 제목이 섞인다

장 제목은 `第一章`, `第二十四章`, 시편은 `第一百五十篇`처럼 **한자 숫자**다. 아라비아 숫자로 옮기는 변환이 필요하고, **`百`와 `零`을 함께 처리해야 한다.**

프로토타입 1차 구현은 `第一百零一篇`을 101이 아니라 100으로 읽어 **시편이 150장이 아니라 141장**으로 집계됐다. 아홉 개가 기존 장과 충돌해 조용히 덮인 것이다.

**표기가 불규칙하다는 점도 확인했다.** 1~150을 전수 조사하면 110은 `一百一十`인데 111·119는 `一百十一`·`一百十九`다. 읽기(한자→정수)는 두 형태를 모두 받아야 하고, **쓰기(정수→한자)는 아예 하지 않는다**([4.1](#41-url-규칙--책-단위-자형은-접두어)).

시편에는 장 제목이 아닌 제목이 **5개** 더 있다.

```
詩篇卷一 · 詩篇卷二 · 詩篇卷三 · 詩篇卷四 · 詩篇卷五
```

시편 제목 총 155개 = 150장 + 권 구분 5개(실측). `第…章|篇` 형식만 장으로 인정하면 자연히 걸러진다.

### 4.5 함정 3. 敬空 공백은 사라진다

1919년 神판은 신명 앞에 전각 공백을 넣는 조판 관행(敬空/挪抬)을 따른다.

```
원문 그대로       '起初　神創造天地。'
_normalize_text  '起初 神創造天地。'          ← U+3000 → 보통 공백
+ CJK 규칙        '起初神創造天地。'           ← 양쪽이 CJK라 제거
```

전권에서 **3,557절(11.4%)**이 이 공백을 갖고 있고, 관측된 모든 사례가 神 또는 主 앞이다.

**결정: 그대로 둔다(제거).** 근거는 셋이다.

- 낱말은 하나도 바뀌지 않는다. 사라지는 것은 조판 관행이다.
- U+3000을 살리려면 CJK 규칙에서 예외를 만들어야 하는데, 이는 JPNMEB 작업에서 정한 「U+3000은 이미 `_normalize_text`가 접는다」는 계약과 정면으로 어긋난다([CLAUDE.md](../CLAUDE.md) 파서 계약).
- 제2 증인(ibibles)은 절 첫머리에도 敬空을 넣는 등 표기가 일정하지 않아, 보존을 택하면 어느 관행을 따를지 다시 정해야 한다.

> 이것은 **선택이지 부작용이 아니다.** 이 설계는 제거를 택했고 예상 절 수는 그 기준이다. 원문 조판을 그대로 보존해야 하는 요구가 있다면 이 설계를 바꿔야 하고, 그때는 CJK 규칙 전체를 다시 봐야 한다.

### 4.6 함정 4. 숫자가 아닌 `sup`이 섞여 있다

신약 16권에 1919년판의 난외 상호참조가 살아 있다. 절 안에 마커가 있고, 장 끝 `dl/dd`에 본체가 있다.

```html
<p><span id="1:23"><sup>23</sup></span>說、『<sup><a href="#1a">〡</a></sup>必有童女、懷孕生子、…</p>
…
<dl><dd><span id="1a"></span><sup>〡</sup><a href="…/以賽亞書#7:14">賽七 〡〤</a></dd></dl>
```

마커는 **蘇州숫자**(〡〢〣〤〥)다. 세 가지를 지켜야 한다.

1. **`sup` 텍스트는 어떤 경우에도 본문이 아니다.** 절 번호든 상호참조 마커든 마찬가지다.
2. **숫자가 아닌 `sup`은 절을 시작하지 않는다.** 절 번호로 읽으려 하면 그 자리에서 절이 끊긴다.
3. **`dd` 안의 내용은 본문이 아니다.** 장 끝에 있으므로, `p`만 순회하지 않고 컨테이너 전체를 훑으면 마지막 절에 각주가 붙는다.

책별 분포(실측): 마태 50, 로마 54, 히브리 38, 사도 28, 마가 21, 누가 22, 요한 19, 고전 14, 갈 12, 고후 9, 벧전 7, 약 5, 엡 5, 딤전·딤후 2, 벧후 1. **구약에는 없다.**

### 4.7 소자주(小字註)는 절 본문에 들어간다

1919년판은 이문·설명을 절 안에 작은 글씨로 넣는다. 維基文庫는 `<small>`로 표현하고 괄호 〈 〉는 투명 글씨로 감싸 둔다.

```
창 4:1  …生了該隱、〈就是得的意思〉便說、耶和華使我得了一個男子。
마 1:25 …等他生了兒子、〈有古卷作等他生了頭胎的兒子〉就給他起名叫耶穌。
```

전권에 `small`이 **1,211개**, 그중 소자주로 분류되는 것이 1,026개이며, **998절(3.2%)**이 〈 〉를 포함한다.

**그대로 두기를 권고한다.** 인쇄본이 본문 안에 넣은 것이고, 제2 증인(ibibles)도 같은 자리에 〔 〕로 싣는다([7.7](#77-제2-증인-대조)의 괄호 치환 약 1,015건이 이것이다). 제거하려면 어디까지가 주석인지 판정해야 하는데, `small`에는 소자주가 아닌 것도 185개 섞여 있어 기계적으로 가를 수 없다.

### 4.8 함정 6. 시편 표제가 1절 안에 들어 있다

시편 표제는 별도 요소가 아니라 **1절 문단의 첫머리**에 있다.

```html
<p><span id="23:1"><sup>1</sup></span><small>大衞的詩。</small>耶和華是我的牧者．我必不至缺乏。 </p>
```

그대로 파싱하면 시 23:1이 「大衞的詩。耶和華是我的牧者…」가 된다. 전권에서 **116편**이 이렇다.

이 저장소의 관례는 표제를 **저장하지 않는 것**이다(KJV·NKRV·WEB·ASV·JPNMEB·KOUGO 모두). RVR1909만 예외인데, 그것은 **소스가 표제를 1절에 녹여 놓아 분리할 수 없기 때문**이다([CLAUDE.md](../CLAUDE.md) 파서 계약).

**여기서는 분리할 수 있다.** 마크업이 표제를 `<small>`로 감싸므로 관례를 따를 수 있다. **결정: 저장하지 않는다.** 규칙과 실측은 이렇다.

> **시편에서, 1절 `sup` 바로 뒤에 오는 `<small>`이며 그 내용이 〈로 시작하지 않으면 표제다.**

| 검사 | 결과 |
| --- | --- |
| 규칙에 걸리는 시편 | **116편** |
| 시편 밖 오탐 | **0건** |
| 좁히지 않았을 때 오탐 | 14권 이상 — 창 4:1 `〈就是得的意思〉`처럼 1절이 소자주로 시작하는 곳 |

〈로 시작하는 것을 빼는 조건이 반드시 필요하다. 그것이 없으면 [4.7](#47-소자주小字註는-절-본문에-들어간다)에서 남기기로 한 소자주를 시편 밖에서 지우게 된다.

시 120편처럼 **표제 안에 소자주가 중첩**된 경우가 있다(`<small>上行<small>〈或作登堦下同〉</small>之詩。</small>`). 표제를 통째로 제거하면 그 안의 소자주도 함께 사라지는데, 표제의 일부이므로 그것이 맞다.

> 이 결정이 제2 증인 대조를 얼마나 바꾸는지 실측했다. **바꾸지 않는다.** 시편 1절 150개 중 표제를 남겼을 때 이미 **132개가 어긋나 있었고**(이체자·괄호 표기 때문), 표제를 빼도 같은 132개다. 일치하던 18개는 애초에 표제가 없는 편이다. 즉 제거는 이미 다른 이유로 어긋나 있던 절만 건드린다.

### 4.9 마지막 장 뒤에 라이선스 상자가 있다

각 책 페이지 끝에는 퍼블릭 도메인 안내 문단이 붙는다. **`sup`이 없는 문단이며 전권에 132개**(66권 × 2)다.

```
此作品在全世界都屬於公有領域，因為作者逝世已經超過100年，且作品於1931年1月1日之前出版。
Public domainPublic domainfalsefalse
```

문서 구조상 **마지막 장 제목 뒤에 오므로**, 절 텍스트를 "다음 마커까지 계속 누적"하는 방식으로 짜면 각 책 마지막 절에 이 문구가 붙는다. 절 수도 연속성도 정상이라 자동 검사로 잡히지 않는다.

**대응은 절 텍스트를 문단 단위로 끊는 것이다.** 문단에 `sup`이 하나도 없으면 그 문단은 어느 절에도 속하지 않는다. 전권에서 `sup` 없는 문단 132개는 **전부 라이선스 상자**였고 본문은 하나도 없었다(실측).

### 4.10 자형 변환은 소스가 해 준다

`/zh-hans/`는 같은 문서를 MediaWiki 자형 변환으로 내려준다. 창세기로 확인한 결과:

```
장 수      hant=50  hans=50
절 수      hant=1533 hans=1533
장·절 구조  완전 동일
1:1        起初　神創造天地。 / 起初　神创造天地。
2:14       伯拉河 / 伯拉河        ← 1919년 지명 유지
```

즉 **간체판은 별도 텍스트가 아니라 같은 원문의 변환 결과**다. 두 역본을 적재해도 절 구조가 어긋날 여지가 없다.

## 5. 코드 변경 지점

### 5.1 `scraper.py` — 책 페이지 캐시 재사용

이 소스도 페이지가 책 단위다. **직전 작업에서 jpn.bible용으로 만든 구조가 그대로 맞는다.**

```python
def _fetch_soup(self, url: str) -> BeautifulSoup:
    if self._is_jpnbible_source():
        return self._fetch_jpnbible_chapter_soup(url)
    if self._is_wikisource_source():
        return self._fetch_wikisource_chapter_soup(url)
    ...
```

다만 장 분리 기준이 다르다. jpn.bible은 `main.book > div[id]`로 잘렸지만, 維基文庫는 **장 제목과 다음 장 제목 사이**를 잘라야 한다.

```python
def _split_wikisource_book(html: str) -> dict[str, str]:
    """Split a book page into {chapter number as string: chapter HTML}."""
    # h2/h3 headings are the only chapter boundary; 詩篇卷N and other section titles
    # do not match the 第…章|篇 form and are skipped, so their paragraphs stay with the
    # preceding chapter rather than starting a new one.
```

캐시 규약은 jpn.bible과 동일하다 — 직전 책 하나만 유지하고, 키는 프래그먼트와 같은 **문자열**이며, 요청이 실패하면 캐시를 채우지 않는다.

### 5.2 `scraper.py` — 파서

체인 위치는 **jpnbible 뒤, `bibletable` 앞**이다. 판별자는 `div.mw-parser-output` 안에 `p > sup`가 있는 것으로는 부족하다(위키문헌의 다른 문서도 그럴 수 있다). **장 슬라이스에 `第…章|篇` 제목이 하나 있고 `sup` 마커가 있을 때만** 처리한다.

```python
WIKISOURCE_CHAPTER_PATTERN = re.compile(r"^第([一二三四五六七八九十百零〇\d]+)[章篇]")
# 「編輯」 링크와 목차 표는 본문이 아니다. sup.reference 는 위키 각주 표시로, 이 문서에는
# 없지만 편집으로 생길 수 있어 함께 제거한다.
WIKISOURCE_REMOVABLE_SELECTOR = "span.mw-editsection, table, style, sup.reference"
```

절 조립 규칙:

| 노드 | 처리 |
| --- | --- |
| `p` 안의 **숫자** `sup` | 절 시작. **연달아 나오면 그 번호들이 한 범위** |
| `p` 안의 **비숫자** `sup` | 상호참조 마커. 절을 시작하지 않는다([4.6](#46-함정-4-숫자가-아닌-sup이-섞여-있다)) |
| `sup` 내부 텍스트 | 어떤 `sup`이든 본문 아님 |
| `dl` / `dd` | 상호참조 각주 본체. 본문 아님 |
| `small` 내부 텍스트 | 소자주. **본문에 포함한다**([4.7](#47-소자주小字註는-절-본문에-들어간다)) |
| 시편 1절 첫 `small` (〈로 시작하지 않음) | **시편 표제. 저장하지 않는다**([4.8](#48-함정-6-시편-표제가-1절-안에-들어-있다)) |
| 그 밖의 텍스트 | 현재 범위에 누적 |
| 문단 경계 | 공백 하나, 그 뒤 `CJK_JOIN_PATTERN`이 CJK 사이에서 제거 |

**누적 범위는 문단 하나로 제한한다.** 문단을 넘어 다음 마커까지 누적하면 각 책 마지막 절에 라이선스 상자가 붙는다([4.9](#49-마지막-장-뒤에-라이선스-상자가-있다)).

한자 숫자 변환은 `百`/`十`/`零`을 처리해야 한다([4.4](#44-함정-2-장-제목이-한자-숫자이고-시편에는-장이-아닌-제목이-섞인다)). 변환 결과가 그 책의 장 수 범위를 벗어나거나 이미 나온 장과 겹치면 **파싱 오류로 보고 건너뛴다.** 조용히 덮으면 시편이 141장이 된다.

### 5.3 `scrape_bible_to_db.py` — 역본 등록

```python
ENTRY_URL_ENV_BY_TRANSLATION_TYPE = { ..., "CUVT": "CUVT_ENTRY_URL", "CUVS": "CUVS_ENTRY_URL" }
TRANSLATION_TYPES_BY_LANGUAGE_CODE = { ..., "zh": ("CUVT", "CUVS") }
ENTRY_URL_PREFERENCE_ORDER = (..., "KOUGO", "CUVT", "CUVS")
TRANSLATION_SOURCE_REQUIREMENTS = {
    ...,
    "CUVT": {"source": "wikisource", "version": "zh-hant", "name": "聖經和合本", "language_code": "zh"},
    "CUVS": {"source": "wikisource", "version": "zh-hans", "name": "圣经和合本", "language_code": "zh"},
}
```

- `get_source_version()`은 이 소스에서 **경로의 자형 세그먼트**(`zh-hant` / `zh-hans`)를 돌려준다. **`/wiki/` 형식 URL을 주면 안 된다** — 위키문헌의 기본 형식(`.../wiki/聖經_(和合本)/創世記`)도 200으로 응답하지만(실측), 그때 버전 토큰이 `wiki`가 되어 어느 역본에도 맞지 않는다. 엔트리 URL 검증에서 걸러야 한다. eBible이 역본 코드를, jpn.bible이 `kougo`를 경로에서 읽는 것과 같은 자리다. 이 값이 `None`이면 한 소스의 두 역본을 구별할 수 없어 [7.8](#78-잘못-적재-방지-검증)의 방어선이 무너진다.
- `resolve_book_code_for_source()`는 `None`을 돌려준다. 책 이름은 `bible_book.book_key`가 아니라 **번체 책 이름 상수표**를 쓴다.
- `translation_type`은 요청대로 **`CUVT`(번체) / `CUVS`(간체)**를 쓴다. 기존 30개 값 및 널리 쓰이는 약칭과 겹치지 않는다.

### 5.4 기존 동작이 바뀐다 — `zh`가 처음 생긴다

`zh`는 지금까지 `TRANSLATION_TYPES_BY_LANGUAGE_CODE`에 없던 언어다. 두 역본을 함께 등록하므로 **처음부터 모호**하다.

```
CUVT_ENTRY_URL + CUVS_ENTRY_URL 을 모두 설정 + BIBLE_LANGUAGE_CODE=zh
  → ValueError: Ambiguous entry URL … matches CUVT_ENTRY_URL, CUVS_ENTRY_URL
```

`en`·`es`·`ja`에서 이미 겪은 것과 같은 성질이며, 조용히 한쪽을 고르는 것보다 낫다. **실행 예에는 반드시 `BIBLE_TRANSLATION_TYPE`을 함께 적는다**([9.2](#92-실행-예)).

## 7. 검증

### 7.1 구조 검증

```sql
SELECT COUNT(DISTINCT b.id), COUNT(DISTINCT c.id), COUNT(v.id)
FROM public.bible_book b
JOIN public.bible_chapter c ON c.book_id = b.id
JOIN public.bible_verse  v ON v.chapter_id = c.id
WHERE b.translation_id = :tid;
-- 기대: 66 / 1189 / 31102   (B안 기준. A안이면 31032)
```

연속성 질의는 다른 역본과 동일하며 **0행**이어야 한다.

### 7.2 인코딩·자형 검증

한자가 한 글자도 없는 절을 찾는다.

```sql
SELECT COUNT(*) FROM public.bible_verse v … WHERE b.translation_id = :tid AND v.text !~ '[一-鿿]';
-- 기대: 0행
```

**자형이 역본과 맞는지도 본다.** 번체 역본에 간체 고유자가 섞이면 변환 경로가 잘못된 것이다.

```sql
-- CUVT 에 간체 고유자가 있는가
SELECT COUNT(*) FROM public.bible_verse v … WHERE b.translation_id = :cuvt AND v.text ~ '[创说灵见]';
-- 기대: 0행
-- CUVS 에 번체 고유자가 있는가
SELECT COUNT(*) FROM public.bible_verse v … WHERE b.translation_id = :cuvs AND v.text ~ '[創說靈見]';
-- 기대: 0행
```

### 7.3 판본 검증 — 1919년판인지 확인

**이 역본에서 가장 중요한 검증이다.** 개정판이 섞이면 낱말이 조용히 바뀐다.

```sql
SELECT b.book_order, c.chapter_number, v.verse_number, v.text
FROM public.bible_verse v …
WHERE b.translation_id = :tid
  AND (b.book_order, c.chapter_number, v.verse_number) IN ((1,2,14),(1,29,32),(1,14,15));
```

| 절 | 1919년판이면 | 1988년판이면 |
| --- | --- | --- |
| 창 2:14 | 伯拉河 / 伯拉河 | 幼發拉底河 / 幼发拉底河 |
| 창 29:32 | 流便 / 流便 | 呂便 / 吕便 |
| 창 14:15 | 大馬色 / 大马色 | 大馬士革 / 大马士革 |

세 절 모두 왼쪽이어야 한다. 하나라도 오른쪽이면 소스가 바뀐 것이다.

### 7.4 KJV 대조 — 네 개 장

장별 절 수를 KJV와 맞춰 보면 **정확히 4개 장에서만** 달라야 한다. 총계는 양쪽 다 31,102라서 총계 비교로는 아무것도 걸러지지 않는다.

| 장 | KJV | 和合本 | 성격 |
| --- | ---: | ---: | --- |
| 대상 21 | 30 | **31** | KJV 22:1이 和合本에서 21:31이다 |
| 대상 22 | 19 | **18** | 위와 같은 경계 이동의 뒷면 |
| 요 7 | 53 | **52** | KJV 7:53이 和合本에서 8:1 앞부분이다 |
| 요삼 1 | 14 | **15** | 일본어 역본들과 같은 절 구분 |

**넷 다 절 구분 차이이고 본문이 사라진 것이 아니다.** 제2 증인으로 확인했다 — 대상 21/22는 ibibles도 31/18이고, 요한 7장은 ibibles가 7:53을 **빈 절**로 두고 본문은 8:1에 싣는다. 그 빈 절 하나가 [7.7](#77-제2-증인-대조)에서 "ibibles에만 1"로 나타나는 절이다.

### 7.5 시편 표제 검증

표제를 빼기로 했으므로([4.8](#48-함정-6-시편-표제가-1절-안에-들어-있다)) 시편 1절이 표제로 시작하면 안 된다.

```sql
SELECT c.chapter_number, left(v.text, 24)
FROM public.bible_verse v
JOIN public.bible_chapter c ON c.id = v.chapter_id
JOIN public.bible_book b ON b.id = c.book_id
WHERE b.translation_id = :tid AND b.book_order = 19 AND v.verse_number = 1
  AND left(v.text, 20) ~ '(的詩|之詩|訓誨詩|交與伶長|金詩|的祈禱|流離歌)。'
ORDER BY 1;
-- 기대: 0행 (표제를 남기기로 정했다면 116편)
```

**`left(..., 20)`과 끝의 `。`를 빼면 안 된다.** 표제 어구는 본문 안에도 나온다 — 시 17:1은
「…求你留心聽我這不出於詭詐嘴唇的**祈禱**。」로 끝나므로, 위치를 묶지 않으면 정상 적재에서도
1건이 걸려 **오탐이 상시로 뜬다**(실측). 간체 역본에는 간체 어구(`的诗|之诗|…`)를 쓴다.

반대 방향도 본다. 시편 밖에서 소자주가 사라지지 않았는지 확인한다.

```sql
SELECT COUNT(*) FROM public.bible_verse v … WHERE b.translation_id = :tid AND v.text LIKE '%〈%';
-- 기대: 998행 근처. 0이면 <small> 을 통째로 지운 것이다
```

### 7.6 병합 절 검증

69건 전부가 범위 안에서 같은 본문이어야 한다. 대표 세 건:

```sql
-- 창 24:29-30, 시 8:6-8(폭 3), 그리고 민수기 1장의 연속 병합
… AND (b.book_order, c.chapter_number, v.verse_number) IN
    ((1,24,29),(1,24,30), (19,8,6),(19,8,7),(19,8,8), (4,1,20),(4,1,21));
-- 기대: 각 범위 안에서 text 동일
```

### 7.7 제2 증인 대조

`cut.ibibles.net`(번체) 66권을 전량 대조했다. 결과는 이렇다.

```
維基文庫 31,102절 / ibibles 31,103절
일치 19,302 / 불일치 11,800 / 維基文庫에만 0 / ibibles에만 1
```

표제 제거는 이 수치를 **바꾸지 않는다.** 시편 1절은 표제를 남기든 빼든 132개가 어긋난다([4.8](#48-함정-6-시편-표제가-1절-안에-들어-있다)). 적재 후 실제 대조에서도 **같은 11,800**이 나왔다.

"ibibles에만 1"은 **요한 7:53**이다. ibibles는 그 번호를 빈 절로 남겨 두고 본문은 8:1에 싣는 반면, 維基文庫는 번호 자체를 두지 않는다([7.4](#74-kjv-대조--네-개-장)). 빈 절을 만들지 않는 쪽이 이 저장소의 계약에 맞는다.

불일치가 많아 보이지만 **성격이 하나다.** 문자 치환 빈도 상위는 전부 異體字이거나 괄호 표기다.

| 維基文庫 | ibibles | 건수 |
| --- | --- | ---: |
| 衆 | 眾 | 1,841 |
| 衞 | 衛 | 1,255 |
| 〈 〉 | 〔 〕 | 약 1,015 |
| 爲 | 為 | 567 |
| 豫 | 預 | 455 |
| 旣 | 既 | 381 |
| 眞 | 真 | 317 |
| 羣 | 群 | 283 |
| 汚 | 污 | 259 |
| 塲 | 場 | 155 |

**維基文庫 쪽이 일관되게 옛 자형이다**(衆·衞·爲·豫·旣·眞·羣·汚·塲·徧·牀·裏·着). 이는 그 문서가 「1919년 원판 문자를 쓰고 출판 당시 용자 관습에 맞춰 조정했다」고 밝힌 것과 일치하며, **1919년판에 더 충실하다는 근거**로 본다.

단, 이체자로 설명되지 않는 것이 하나 있다. **`的` → `地` 치환이 80건**이다. 부사격 조사 표기 차이이며 두 증인 중 어느 쪽이 인쇄본과 같은지는 이 문서에서 판정하지 못했다([3.1](#31-확인하지-못한-것)). 적재 후 정오표 작업 대상이다.

> 이 대조는 합격/불합격 판정이 아니라 **정오표를 만드는 작업**이다. 두 증인 모두 정본이 아니다.

### 7.8 잘못 적재 방지 검증

`TRANSLATION_SOURCE_REQUIREMENTS`가 양방향으로 막는지 확인한다.

- `CUVT` 역본에 `/zh-hans/` 엔트리 URL을 주면 거부되어야 한다(버전 토큰 불일치).
- `zh` 두 역본이 모두 설정된 상태에서 `BIBLE_LANGUAGE_CODE=zh`만 주면 예외여야 한다([5.4](#54-기존-동작이-바뀐다--zh가-처음-생긴다)).

인라인 HTML 픽스처로 추가한다. **네트워크를 타는 테스트는 넣지 않는다.**

| 테스트 | 검증 내용 |

| `test_wikisource_ignores_crossref_sup` | 蘇州숫자 `sup`이 절을 끊지 않고 본문에도 안 섞임 |

한자 숫자 테스트가 특히 중요하다. 이것이 깨지면 **시편이 141장이 되고도 다른 검사는 전부 통과한다.**

## 9. 운영 계획

### 9.1 요청 간격과 소요

- 維基文庫는 위키미디어 재단 사이트다. `robots.txt`가 고속 크롤러에 경고를 두고 있으므로 **기존 1초 하한을 그대로 적용**한다.
- 역본당 HTTP 요청은 **66회**, 두 역본 합쳐 **132회**다. 전송량은 번체 66권 기준 약 12 MB(실측, 비압축). 가장 큰 창세기가 385 KB다.
- 소요는 HTTP가 아니라 DB 쓰기가 지배한다. 직전 KOUGO 적재(1,189장)가 약 14분이었으므로 역본당 비슷하게 잡는다.

### 9.2 실행 예

```bash
# 파서만 확인 (DB 미접속)
CUVT_ENTRY_URL='https://zh.wikisource.org/zh-hant/聖經_(和合本)/創世記#第一章' \
BIBLE_TRANSLATION_TYPE=CUVT python3 scrape_bible_to_db.py --test-genesis1

# 번체 전권
BIBLE_TRANSLATION_ID=<tid> BIBLE_TRANSLATION_TYPE=CUVT BIBLE_LANGUAGE_CODE=zh \
CUVT_ENTRY_URL='https://zh.wikisource.org/zh-hant/聖經_(和合本)/創世記#第一章' \
  python3 scrape_bible_to_db.py --start-book 1 --end-book 66
```

`BIBLE_TRANSLATION_TYPE`을 빼면 `zh` 역본이 둘이라 실패한다([5.4](#54-기존-동작이-바뀐다--zh가-처음-생긴다)).

### 9.3 갱신 문제

- **위키는 언제든 편집된다.** 이것이 이 소스의 가장 큰 운영상 성질이며, 고정 판본을 서비스하는 eBible·jpn.bible과 다르다. 적재 시점의 리비전 ID를 함께 기록해 두면 나중에 대조할 수 있다. API로 현재 리비전을 얻고(`action=query&prop=revisions`), `w/index.php?oldid=<id>`로 그 리비전을 고정 조회하는 경로를 실제로 확인했다(창세기 현재 리비전 `2272026`, 2023-04-03).
- 미적재 삽입이라 편집이 자동 반영되지 않는다. 반영하려면 해당 절만 지우고 다시 넣는다. 외래키가 없으므로 **절 → 장 순서**를 지킨다.
- 되돌리기 절차는 [口語訳 설계 §9.4](japanese-colloquial-1955-scraping-design.md)와 동일하며, `translation_type`만 바꿔 쓰면 된다.

## 11. 구현 순서

1. **테스트 먼저** — [8](#8-테스트-설계). 한자 숫자·병합 마커·卷 제목·캐시 넷이 핵심이다.
2. `scraper.py` — 소스 판별, URL 빌더, 장 발견(`KJV_CHAPTER_COUNTS` 재사용), 책 페이지 캐시(jpn.bible 구조 재사용), 파서, 체인 편입.
3. `scrape_bible_to_db.py` — 등록 표 4개, `get_source_name`/`get_source_version` 분기.
4. `pytest -q` 전량 통과. **기존 131개가 그대로 통과해야 한다.**
5. `--test-genesis1`, `--test-book 19 --test-chapter 119`(176절), `--test-book 19 --test-chapter 101`(한자 숫자), `--test-book 1 --test-chapter 24`(병합), `--test-book 40 --test-chapter 1`(상호참조·소자주), `--test-book 1 --test-chapter 50`(라이선스 상자)로 DB 없이 확인.
6. **DB 시드** — CHECK 값 2개 → `bible_translation` 2행 → `bible_book` 132행. `bible_book_description`의 `zh` 66행은 별도.
7. 번체 한 권 적재 후 전권, 이어서 간체.
8. [7](#7-검증) 전체 실행. 특히 [7.3](#73-판본-검증--1919년판인지-확인)과 [7.7](#77-제2-증인-대조).

저장소가 요구하는 신규 소스 체크리스트(CLAUDE.md "Adding a new source") 8단계에 더해, 이 소스도 jpn.bible과 같은 **추가 3항목**(`_fetch_soup` 분기와 책 페이지 캐시, 전용 책 이름 상수, 문서 갱신)이 붙는다.

## 12. 리스크

### 리스크 1. 개정판을 1919년판으로 알고 적재 (가장 큼)

eBible 경로가 압도적으로 편하기 때문에 실제로 일어나기 쉽다. 낱말이 조용히 바뀌고, 절 수·연속성 검사는 **전부 통과한다**. [7.3](#73-판본-검증--1919년판인지-확인)의 세 절 조회가 유일한 방어다.

### 리스크 2. 한자 숫자 변환 실패

`第一百零一篇`을 100으로 읽으면 시편이 141장이 되고 아홉 장이 조용히 덮인다. 장 수 대조로 잡히지만, **대조를 돌리지 않으면 드러나지 않는다.**

### 리스크 3. 병합 마커의 뒤 번호 누락

69건에서 70개 번호가 사라진다. 연속성 검사가 잡는다.

### 리스크 4. 자형이 역본과 어긋남

`/zh-hant/`로 받아 `CUVS`에 넣거나 그 반대. 본문이 멀쩡해 보이고 절 수도 맞는다. [7.2](#72-인코딩자형-검증)의 고유자 질의가 방어선이다.

### 리스크 5. 시편 표제 규칙을 넓게 잡음

「1절 첫 `<small>`은 표제」로만 두면 시편 밖 14권 이상에서 소자주가 지워진다(창 4:1 등). 〈로 시작하지 않는다는 조건과 시편 한정이 함께 있어야 한다([4.8](#48-함정-6-시편-표제가-1절-안에-들어-있다)).

### 리스크 6. 책 끝 라이선스 상자가 마지막 절에 붙음

66권 모두에서 마지막 절만 오염된다. 절 수·연속성·빈 절 검사를 **전부 통과한다.** 마지막 절 길이를 훑거나 `公有領域`을 조회하는 것이 유일한 방어다([4.9](#49-마지막-장-뒤에-라이선스-상자가-있다)).

### 리스크 7. 위키 편집으로 본문이 바뀜

고정 판본이 아니다. 적재 시점 리비전을 기록해 두지 않으면 나중에 무엇이 바뀌었는지 알 수 없다([9.3](#93-갱신-문제)).

### 리스크 8. `zh` 책 설명 66행을 적재 조건으로 오해

`bible_book_description`은 본문 적재와 무관하다. 없어도 적재는 되므로, 이것 때문에 적재를 미루지 않는다.

## 12.5 적재 결과 (실측)

`CUVT translation_id=38 / translation_order=35`, `CUVS translation_id=39 / translation_order=36`. 2026-08-25 적재.

```
역본당 66권 / 1,189장 / 31,102절      ← 설계 예상치와 정확히 일치
연속성이 깨진 장                       0 / 0
한자가 없는 절                         0 / 0
시편 표제가 남은 편                     0 / 0
敬空(전각 공백)이 남은 절               0 / 0
라이선스 문구 누출                      0 / 0
〈 주석이 남은 절                      997 / 997
```

| 검증 | 예상 | 실측 |
| --- | --- | --- |
| HTTP 요청 수 | 역본당 66 | 66 / 66 |
| 자형 배타성 | 서로 섞이지 않음 | CUVT에 간체 고유자 0(번체 9,889절), CUVS에 번체 고유자 0(간체 9,889절) |
| 판본(1919) | 伯拉河·大馬色·流便 | 두 역본 모두 그대로 |
| KJV와 다른 장 | 4 (대상 21·22, 요 7, 요삼 1) | 같음. 31/18/52/15 |
| 병합 창 24:29-30 | 두 번호에 같은 본문 | 그대로 |
| 두 역본 절 구조 | 완전 동일 | 차이 0 |
| 제2 증인 대조 | 11,800 | **11,800** |

두 역본이 **같은 원문의 자형 변환**이라는 설계 전제가 적재 결과로 확인됐다 — 절 구조 차이 0, 주석 절 수 997로 동일, 이체자 통계도 대칭이다.

### 구현하며 드러난 것

- **제2 증인 대조 예측이 틀렸다.** 이 문서는 표제를 빼면 시편에서 116절이 더 어긋난다고 적었는데, 실측하니 총계가 11,800 그대로였다. 시편 1절은 표제를 남기든 빼든 **이미 132개가 이체자 때문에 어긋나 있었기** 때문이다. 예측을 실측으로 바꿨다.
- **[7.5](#75-시편-표제-검증)의 검증 질의가 오탐을 냈다.** 위치를 묶지 않은 정규식이 시 17:1의 본문 끝 「…嘴唇的祈禱。」에 걸려, 정상 적재에서도 1건이 상시로 뜬다. `left(v.text, 20)`과 끝의 `。`를 붙여 0건으로 만들었다.
- **jpn.bible에 넣은 방어를 여기엔 빠뜨렸다.** 책 페이지 전체를 파서에 넘기면 67절짜리 그럴듯한 목록이 나왔다. 절 `id`의 장 번호를 읽어 장이 섞이면 `[]` + 경고로 바꿨다.
- 책 페이지 캐시를 소스 중립으로 일반화해(`_fetch_book_page_chapter_soup`) jpn.bible과 공유한다. 분리 기준만 인자로 넘긴다.

## 13. 결론

제시된 판단 — **1919년 화합본이 가장 안전한 기본 판본**이고 **출처가 명확한 데이터셋을 써야 한다** — 는 실측으로 뒷받침된다. 그리고 두 번째 문장이 실제로 걸림돌이 된다.

가장 편한 소스(eBible, 기존 어댑터 재사용)는 **1919년판이 아니라 1988년 新標點和合本**이고, 그 개정분의 권리에 대해 배포처 표기와 홍콩 교계 문헌이 어긋난다. 반면 維基文庫는 1919년판임이 세 지표로 확인되고, 1931년 이전 발행이라는 관할 무관한 PD 근거를 문서에 달고 있다.

- 소스: `https://zh.wikisource.org/zh-{hant,hans}/聖經_(和合本)/{책}` — 역본당 66 요청
- 예상 적재량: 역본당 66권 / 1,189장 / **31,102절** (KJV 총계와 같으나 장별로는 4개 장이 다르다)
- 구조 변경: jpn.bible의 책 페이지 캐시 재사용 + 새 파서 1개
- 파서 함정: 병합 마커 69, 한자 숫자 장 제목, 卷 제목 5개, 敬空 3,557절, 상호참조 `sup` 289, 소자주 998절, 책 끝 라이선스 상자 132문단
- DB 선행: CHECK 값 2개, `bible_translation` 2행, `bible_book` 132행, (별도) `bible_book_description` `zh` 66행

미결정은 없다. 세 가지 선택을 모두 확정했다 — **병합 절은 B안**, **敬空은 제거**, **시편 표제는 미저장**. 예상 절 수 31,102는 이 기준의 값이다.
