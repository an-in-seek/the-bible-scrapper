# 일본어 퍼블릭 도메인 성경 본문 스크래핑 개발 설계

## 1. 목적

퍼블릭 도메인인 일본어 성경 66권 전체를 스크래핑하여 기존 PostgreSQL 스키마(`bible_chapter`, `bible_verse`)에 적재한다.

### 1.1 원본 문서 분석

이 문서의 전신(`docs/sadfasdf-scraping-design.md`)은 **설계 문서가 아니었다.** 어떤 판본을 고를지에 대한 메모 일부(3장 도입부)만 있었고, 스크래핑 설계에 필요한 항목은 하나도 없었다.

| 설계 문서에 필요한 것 | 원본에 있었나 |
| --- | --- |
| 대상 사이트 · URL 규칙 | 없음 |
| DOM 구조 · 파싱 규칙 | 없음 |
| 코드 변경 지점 | 없음 |
| DB 선행 조건 | 없음 |
| 검증 방법 | 없음 |
| 판본 후보와 근거 | **있음** (이 문서 1.2~1.3에서 검토) |

따라서 원본에서 살릴 수 있는 것은 **판본 후보 목록**뿐이다. 그 부분을 검증한 결과가 아래다.

### 1.2 원본 문서의 법적 서술은 뒤집혀 있다

원본은 두 후보를 이렇게 평가했다.

> 1순위 (현대 구어체 필요 시): 1955년 구어역 (口語訳, JBS 1955)
> … **저작권 만료가 확인되어** 오픈소스 DB로 가장 널리 유통되는 표준 텍스트입니다.
>
> 2순위 (고전 문어체 필요 시): 메이지 모토야쿠(구약) + 다이쇼 개역(신약)
> **법적으로 티끌 하나 없는** 완전한 고전 텍스트이나 …

**실측 결과 두 평가의 위치가 서로 바뀌어 있다.** 일본어 위키문헌의 해당 문서들을 조회했다.

| 문서 | 상태 |
| --- | --- |
| `創世記(口語訳)` | **著作権侵害のおそれ · 삭제 논의 중** |
| `詩篇(口語訳)` | **著作権侵害のおそれ · 삭제 논의 중** |
| `マタイによる福音書(口語訳)` | **삭제 논의 중** |
| `口語旧約聖書` · `口語新約聖書` (목차) | 삭제 논의 중 |
| `大正改訳新約聖書` | 퍼블릭 도메인 템플릿, 분쟁 없음 |
| `明治元訳旧約聖書` | 퍼블릭 도메인 템플릿, 분쟁 없음 |

口語訳 본문 문서에는 다음 경고가 붙어 있다.

```
この項目は 著作権 侵害が指摘され、現在審議中です。
審議の結果、該当する投稿以降の版全て もしくは この項目自体 が
履歴も含めて削除される可能性があります。
```

반면 明治元訳/大正改訳에는 근거가 명시된 퍼블릭 도메인 템플릿이 붙어 있다.

```
この作品は1931年1月1日より前に発行され、かつ著作者の没後
（団体著作物にあっては公表後又は創作後）100年以上経過しているため、
全ての国や地域で パブリックドメイン の状態にあります。
```

즉 원본이 "저작권 만료가 확인되어"라고 쓴 쪽이 **분쟁 중**이고, "법적으로 티끌 하나 없는"이라고 쓴 쪽이 실제로 깨끗하다.

> **口語訳(1955)은 이 설계에서 채택하지 않는다.** 요청이 "퍼블릭 도메인"인데 배포처 스스로 저작권 침해 여부를 심사 중인 텍스트를 기반으로 삼을 수 없다. 널리 유통된다는 사실은 권리 관계를 증명하지 않는다.
>
> 이 문서는 법률 자문이 아니다. 위 내용은 배포처의 표기를 조회한 결과이며, 실제 채택 판단은 사용자 몫이다.

### 1.3 후보 비교와 선택

원본에 없던 세 번째 후보를 조사에서 찾았다. eBible.org가 제공하는 **フリーダム・バイブル(Japanese Freedom Bible, `jpnm`)**이다.

| 후보 | 라이선스 | 소스 | 어댑터 비용 | 문체 | 판정 |
| --- | --- | --- | --- | --- | --- |
| **`jpnm` フリーダム・バイブル** | 발행처가 **Public Domain 명시** | ebible.org | **거의 0** (기존 어댑터 재사용) | 현대 구어체 | **채택** |
| 文語訳 (明治元訳 + 大正改訳) | 근거 명확한 PD | ja.wikisource | **높음** (신규 소스, 책별 구조 상이) | 고전 문어체 | 대안([10](#10-대안-경로--文語訳)) |
| 口語訳 (JBS 1955) | **분쟁 중** | ja.wikisource (삭제 논의) | — | 현대 구어체 | 채택 불가 |

`jpnm` 배포처 표기(실측):

```
フリーダム・バイブル  Japanese Freedom Bible
Language: [jpn] 日本語   ID: JPNMEB or jpnm   public domain
この聖書翻訳には著作権が設定されていません。
この聖書翻訳の公式な配布元は eBible.org です。これは翻訳の草案です。
```

원본이 요구한 "현대 구어체"를 만족하면서 권리 관계가 깨끗하고, **이미 붙어 있는 eBible 어댑터를 그대로 쓴다.** 마지막 문장이 걸림돌인데, `これは翻訳の草案です`(초안)라는 점은 SBLM과 같은 성격이며 대응 절차도 이미 있다([9.3](#93-초안-갱신-문제)).

## 2. 결론 먼저

1. **소스·URL·HTTP·인코딩·재시도·resume는 변경 0줄.** `jpnm`은 SBLM/RV1909와 같은 사이트·같은 렌더러다. 엔트리 URL만 `https://ebible.org/jpnm/GEN01.htm`으로 주면 된다. 66권 첫 장 전수 프로브 **실패 0건**.
2. **파서에 수정이 하나 필요하다.** 블록 경계에 넣는 공백이 **일본어 본문을 오염시킨다.** 표본 505절 중 **250절(49%)**이 영향을 받고, 시가서는 사실상 전부다(시편 119편 176절 중 173절). 일본어는 단어 사이에 공백을 쓰지 않는다([4.3](#43-함정-1-일본어에-없는-공백이-들어간다)).
3. **생략 절은 추가 작업이 없다.** `jpnm`도 WEB/SBLM과 같은 네 절(눅 17:36, 행 8:37 · 15:34 · 24:7)을 비워 두는데, 직전 작업에서 넣은 `(omitted)` 처리가 **이미 올바르게 동작한다**(실측 확인).
4. **표제·각주·`span.wj` 규칙도 그대로 적용된다.** `div.d` 22개(시편 119편), `div.sp` 9개(아가 1장), `span.wj` 30개(눅 17장)를 관측했고 현재 셀렉터가 정확히 처리한다.
5. **책명은 `ul.tnav`에서 가져온다.** `div.mt`는 여기서도 결함이다 — `書` 하나에 5권(수·룻·스·느·에), `福音書` 하나에 4권(마·막·눅·요)이 뭉친다([6.4](#64-bible_book-66권-시드)).
6. **DB 작업이 SBLM보다 많다.** 일본어 역본이 DB에 하나도 없어서 `bible_book` 66행뿐 아니라 **`bible_book_description`의 `ja` 66행도 신규**다. `language_code` CHECK에 `ja`는 이미 허용되어 있다.

## 4. 대상 페이지 특성

### 4.1 URL 규칙 — 기존과 동일

```
https://ebible.org/jpnm/{USFM대문자}{장번호}.htm
```

장 번호는 책별 자릿수로 0 패딩한다(시편만 3자리). 기존 `_build_ebible_chapter_segment()`가 그대로 적용되며, 역본 코드는 엔트리 URL 경로의 첫 세그먼트에서 읽으므로 **URL 관련 코드 변경은 0줄**이다.

```
source = ebible | code = jpnm | version = jpnm
```

### 4.2 DOM 구조

SBLM과 동일하다. 절 번호는 `span.verse`의 `id`(`V12`)에서 읽고, 본문은 마커 뒤 형제 노드에 있다.

| 클래스 | SBLM | jpnm | 처리 |
| --- | --- | --- | --- |
| `div.p` / `div.q` / `div.q2` / `div.b` | 관측 | 관측 (동일) | 본문, 유지 |
| `div.d` (시편·이합체 표제) | 관측 | 관측 (시편 119편 22개) | 제거 |
| `div.sp` (화자 표시) | 관측 | 관측 (아가 1장 9개) | 제거 |
| `a.notemark` + `span.popup` | 관측 | 관측 | 제거 (2단계) |
| `span.wj` (예수 말씀) | 관측 | 관측 (눅 17장 30개) | **유지** |
| `ruby` / `rt` (후리가나) | — | **0건** | 해당 없음 |

> **후리가나가 없다는 점은 확인이 필요했다.** 일본어 성경 사이트는 흔히 `<ruby>漢字<rt>かんじ</rt></ruby>` 형태로 읽기를 붙이는데, 그대로 파싱하면 본문에 읽기가 섞여 `漢字かんじ`가 된다. `jpnm`은 10개 표본 전부에서 `ruby` 계열 태그가 0개였다. **다른 일본어 소스를 추가한다면 이 검사를 먼저 해야 한다.**

### 4.3 함정 1. 일본어에 없는 공백이 들어간다

**이 문서에서 가장 중요한 항목이다.**

기존 eBible 파서에는 블록 태그를 지날 때 공백을 하나 넣는 규칙이 있다. 한 절이 두 블록에 걸칠 때 단어가 붙지 않게 하려는 것으로, 스페인어·영어에서는 **반드시 필요하다**.

```python
elif node.name in EBIBLE_BLOCK_TAGS and current is not None:
    block_changed = True
```

그러나 **일본어는 단어 사이에 공백을 쓰지 않는다.** 같은 규칙이 여기서는 본문을 오염시킨다.

```
원본 블록:  <div class="q">  1 主は私の羊飼い。  </div>
            <div class="q2"> 私は何も欠けることがない。 </div>

현재 결과:  主は私の羊飼い。 私は何も欠けることがない。    <- 인쇄본에 없는 공백
올바른 값:  主は私の羊飼い。私は何も欠けることがない。
```

산문에서 더 분명하다. 창세기 3:13은 두 `div.p`에 걸치는데, 닫는 괄호와 다음 문장 사이에 공백이 생긴다.

```
현재 결과:  ...何ということをしたのか。」 女は言った。「蛇が私を欺いたので...
올바른 값:  ...何ということをしたのか。」女は言った。「蛇が私を欺いたので...
```

영향 범위 실측(12개 장 505절):

| 장 | 절 수 | 공백 오염 |
| --- | --- | --- |
| `PSA119` | 176 | **173** |
| `ISA40` | 31 | **29** |
| `SNG01` | 17 | 16 |
| `MAT05` | 48 | 8 |
| `GEN03` | 24 | 7 |
| `MRK01` | 45 | 7 |
| `PSA023` | 6 | 6 |
| `ACT08` | 40 | 2 |
| `3JN01`, `LUK17` | 14, 37 | 각 1 |
| `GEN01`, `JHN03` | 31, 36 | 0 |
| **합계** | **505** | **250 (49%)** |

시가서는 사실상 전부다. `div.q`/`div.q2`가 한 절을 여러 줄로 쪼개기 때문이다.

> 이것은 CLAUDE.md가 기록한 bskorea 교훈과 같은 종류다. 그쪽은 `get_text(" ")`가 한국어 조사를 `모세 가`로 쪼개는 문제였고, 여기는 블록 결합 공백이 일본어 문장을 쪼갠다. **언어에 따라 공백 규칙이 다르다**는 사실이 두 번째로 문제가 된 사례다.

**이 오염은 자동 검증을 전부 통과한다.** 절 수도 번호도 정상이고 빈 절도 없다. 전용 쿼리가 없으면 잡히지 않는다([7.3](#73-공백-오염-검증--이-소스-전용)).

### 4.4 생략 절은 추가 작업이 없다

`jpnm`도 WEB/SBLM과 같은 네 절을 비워 둔다. 직전 작업에서 넣은 처리가 그대로 동작하는 것을 확인했다.

```
LUK17:36 -> (omitted) 표기      ACT15:34 -> (omitted) 표기
ACT08:37 -> (omitted) 표기      ACT24:7  -> (omitted) 표기
```

판정 근거가 각주의 존재이고 언어와 무관하므로 **코드 변경이 필요 없다.**

## 5. 코드 변경 지점

### 5.1 `scraper.py` — CJK 공백 제거 (유일한 파서 변경)

블록 결합 공백을 없애는 것이 아니라, **양쪽이 모두 CJK 문자일 때만** 공백을 접는다. 다른 언어는 영향을 받지 않는다.

```python
# Japanese and Chinese put no spaces between words, so the block separator that a
# Spanish or English verse needs must not survive between two CJK characters.
# Hangul (U+AC00-D7A3) is deliberately excluded: Korean does space its words.
CJK_RANGES = "　-〿぀-ヿ㐀-䶿一-鿿＀-￯"
CJK_JOIN_PATTERN = re.compile(rf"(?<=[{CJK_RANGES}])\s+(?=[{CJK_RANGES}])")
```

`_extract_verses_from_ebible_page()`의 정규화 직후에 한 번 적용한다.

**프로토타입 검증 결과** — 언어별 단위 케이스와 실제 데이터 양쪽을 돌렸다.

```
[단위]  OK 한국어    모세가 말하되 여호와께서 이르시니라        (변화 없음)
        OK 스페인어  ¿Qué es lo que has hecho? Y dijo la mujer. (변화 없음)
        OK 영어      Yahweh is my shepherd; I shall lack nothing. (변화 없음)
        OK 일본어    主は私の羊飼い。 私は... -> 主は私の羊飼い。私は...
        OK 괄호경계  したのか。」 女は言った。 -> したのか。」女は言った。
        OK 영문혼재  使徒 Paul は言った                        (변화 없음)

[실측]  PSA023   6절: 오염 6 -> 0        GEN03  24절: 오염 7 -> 0
        PSA119 176절: 오염 173 -> 0      ISA40  31절: 오염 29 -> 0
```

한글을 범위에서 뺀 것이 핵심이다. 한국어는 단어를 띄어 쓰므로 NKRV 본문에 적용하면 안 된다.

> 적용 위치를 eBible 파서로 한정한다. `_normalize_text()`에 넣으면 전 소스에 걸리는데, 지금 CJK 본문을 내보내는 소스는 eBible 하나뿐이라 범위를 넓힐 이유가 없다. 나중에 중국어(`zh`) 소스를 붙일 때 재검토한다.

### 5.2 `scrape_bible_to_db.py` — 역본 등록

SBLM과 같은 5곳이다. 소스는 이미 있으므로 역본 등록만 하면 된다.

```python
ENTRY_URL_ENV_BY_TRANSLATION_TYPE = { ..., "JFB": "JFB_ENTRY_URL" }
TRANSLATION_TYPES_BY_LANGUAGE_CODE = { ..., "ja": ("JFB",) }
ENTRY_URL_PREFERENCE_ORDER = (..., "SBLM", "JFB")
TRANSLATION_SOURCE_REQUIREMENTS = {
    ...,
    "JFB": {
        "source": "ebible",
        "version": "jpnm",          # 경로에서 오는 토큰
        "name": "フリーダム・バイブル",
        "language_code": "ja",
    },
}
```

`version`이 `"jpnm"`인 점이 중요하다. eBible에서 세 번째 역본이므로, `get_source_version()`이 경로 토큰을 돌려주지 않으면 세 역본이 서로 구분되지 않는다. 이 장치는 SBLM 작업에서 이미 들어가 있다.

`translation_type` 값은 `JFB`(Japanese Freedom Bible)를 제안한다. 기존 값 29개와 충돌하지 않고, `jpnm`은 소스 코드라 역본 식별자로는 부적절하다.

`scraper.py`에 기본 엔트리 URL 상수도 추가한다.

```python
DEFAULT_EBIBLE_JFB_ENTRY_URL = "https://ebible.org/jpnm/GEN01.htm"
```

`ja`는 언어별 역본이 하나뿐이라 `BIBLE_LANGUAGE_CODE=ja` 단독 지정으로도 해석된다(`en`/`es`와 달리 모호하지 않다).

## 6. DB 준비

### 6.1 현재 상태 (실측)

```
[bible_translation]        29행. 언어 분포: ko 6 / en 17 / es 4 / de 1 / la 1
                           일본어 역본 0건
[translation_type CHECK]   29개 값, 'JFB' 없음
[bible_book_description]   en 66 / es 66 / ko 66      <- ja 없음
[bible_book]               translation_id 1, 2, 10, 22, 23, 33, 35
[language_code CHECK]      ko, en, zh, ja, es, de, la  <- ja 허용됨
```

**일본어 역본이 하나도 없다.** SBLM은 RVR1909에서 책명과 설명을 물려받을 수 있었지만, 여기는 둘 다 신규다.

### 6.2 `translation_type` CHECK 제약 — 30번째 값

RVR1909(27→28), SBLM(28→29) 때와 동일한 절차다.

1. `pg_get_constraintdef()`로 **현재 정의를 프로그램으로 읽어** 값 목록을 추출한다. 손으로 다시 타이핑하지 않는다.
2. 목록에 `'JFB'`를 더해 제약을 재생성한다.
3. 재생성 후 값 개수가 **29 → 30**인지, 기존 29개가 모두 남았는지 확인한다.

### 6.3 `bible_translation` row

```sql
INSERT INTO public.bible_translation (translation_type, name, language_code, translation_order)
SELECT 'JFB', 'フリーダム・バイブル', 'ja',
       COALESCE(MAX(translation_order), 0) + 1
FROM public.bible_translation;
```

`translation_order`는 **NOT NULL이고 기본값이 없다.** SBLM 시드 때 이걸 빠뜨려 삽입이 거부됐다. `id`를 따라가지 않으므로 기존 최대값 + 1을 쓴다.

### 6.4 `bible_book` 66권 시드

**`div.mt`를 책명 출처로 쓸 수 없다.** 66권 전수 조사 결과 9권이 2개 이름으로 뭉친다.

```
'書'      <- JOS, RUT, EZR, NEH, EST      (ヨシュア記, ルツ記, エズラ記, ネヘミヤ記, エステル記)
'福音書'  <- MAT, MRK, LUK, JHN            (4복음서 전부)
```

`div.mt`와 `ul.tnav`는 66권 중 **38권에서 불일치**한다. `ul.tnav`는 **66권 전부 고유**하므로 이쪽을 쓴다.

```
1  GEN  mt=創世記        nav=創世記
6  JOS  mt=書            nav=ヨシュア記     <- mt 결함
65 JUD  mt=ユダの手紙    nav=ユダ
66 REV  mt=ヨハネの黙示録 nav=ヨハネの黙示録
```

SBLM 때는 적재된 RVR1909 책명을 재사용했지만 **여기는 물려받을 일본어 역본이 없으므로 `ul.tnav`가 유일한 출처다.** 시드 전에 66개 이름이 서로 다른지, 정경 순서와 맞는지 확인한다.

`book_key`는 USFM 코드(`GEN`, `PSA`, `3JN`), `book_order`는 1~66이다. `abbreviation`과 `testament_type`도 **NOT NULL**인데 소스에 약어가 없다. 두 가지 중 하나를 택한다.

| 안 | 내용 |
| --- | --- |
| **A** | 약어를 `book_key`로 채운다(`GEN`). 단순하고 고유성이 보장된다 |
| B | 일본어 관용 약어(`創`, `出`, `詩`)를 수기로 넣는다. 표시 품질은 낫지만 66개를 손으로 만들어야 하고 검증 근거가 없다 |

**A를 권고한다.** 소스에 없는 값을 만들어 넣는 것보다, 출처가 분명한 값을 쓰는 편이 낫다.

### 6.5 `bible_book_description` — `ja` 66행 신규

이 테이블은 `(book_key, language_code)` 키다. 현재 `en`/`es`/`ko` 각 66행이 있고 **`ja`는 없다.**

SBLM은 `es` 행이 이미 있어 추가 작업이 0이었지만, 여기는 66행을 새로 만들어야 한다. RVR1909 때 스페인어 행을 만든 방식과 같이, **기존 영어 행을 번역해** 사실 정보(저자·연대·배경)가 어긋나지 않게 한다.

- 원문 성경 본문에서 생성하지 않는다. 소개문은 스크래핑 대상이 아니다.
- 삽입 후 빈 필드 0건, mojibake 0건을 확인한다.

> 이 작업은 본문 적재와 독립이다. 66권 적재를 먼저 끝내고 별도로 진행해도 된다.

## 7. 검증

### 7.1 구조 검증 (전 소스 공통)

WEB 설계 문서 11.4와 동일하다.

1. 66권 적재 / 2. 장 수 합계 **1,189** / 3. 절이 0개인 장 없음 / 4. 절 번호가 1부터 연속 / 5. 본문 오염 없음

### 7.2 인코딩 검증

eBible은 `Content-Type`에 charset을 선언하지 않는다. `_request_html()`의 `apparent_encoding` 재디코딩이 없으면 본문이 깨진다. 스페인어와 달리 **일본어는 깨지면 한눈에 보이지만**, 쿼리로도 확인한다.

```sql
-- mojibake 및 대체 문자 (기대값 0)
SELECT COUNT(*) FROM public.bible_verse v
JOIN public.bible_chapter c ON c.id = v.chapter_id
JOIN public.bible_book b    ON b.id = c.book_id
WHERE b.translation_id = :tid
  AND (v.text LIKE '%Ã%' OR v.text LIKE '%â%'
       OR v.text LIKE '%' || U&'\FFFD' || '%');
```

```sql
-- 반대 방향: 일본어 문자가 실제로 저장됐는지 (0이면 실패)
SELECT COUNT(*) FROM public.bible_verse v
JOIN public.bible_chapter c ON c.id = v.chapter_id
JOIN public.bible_book b    ON b.id = c.book_id
WHERE b.translation_id = :tid
  AND v.text ~ '[぀-ヿ一-鿿]';
-- 기대값: 3만 건 안팎
```

두 방향을 **모두** 본다. 앞 쿼리만으로는 문자가 통째로 사라진 실패를 놓친다.

### 7.3 공백 오염 검증 — 이 소스 전용

[4.3](#43-함정-1-일본어에-없는-공백이-들어간다)의 오염은 구조 검증을 전부 통과하므로 전용 쿼리가 필요하다.

```sql
-- CJK 문자 사이에 공백이 남았는지 (기대값 0행)
SELECT b.book_key, c.chapter_number, v.verse_number, LEFT(v.text, 60)
FROM public.bible_verse v
JOIN public.bible_chapter c ON c.id = v.chapter_id
JOIN public.bible_book b    ON b.id = c.book_id
WHERE b.translation_id = :tid
  AND v.text ~ '[　-〿぀-ヿ一-鿿＀-￯]\s+[　-〿぀-ヿ一-鿿＀-￯]'
LIMIT 50;
```

수정 전이라면 **절반가량이 걸린다.** 0행이 나와야 [5.1](#51-scraperpy--cjk-공백-제거-유일한-파서-변경)이 실제로 적용된 것이다.

### 7.4 표제 오염 검증

시편 119편(`div.d` 22개)과 아가(`div.sp` 9개)를 확인한다. 일본어판의 표제 문자열은 스페인어와 다르므로 **적재 후 실제 값을 뽑아 쿼리를 만든다.** 추정으로 적으면 통과해도 의미가 없다(SBLM 문서 작성 때 히브리 문자 표제를 `DALET`/`VAU`로 잘못 적어 두 개를 놓칠 뻔했다).

### 7.5 기존 역본 대조

같은 DB의 KJV(`translation_id=10`)와 절 번호를 양방향으로 대조한다. **차이가 곧 누락은 아니다** — RV1909 대 SBLM에서 확인했듯 대부분은 절 병합·이동이다. 차이 항목은 인접 절 본문을 눈으로 확인해 분류한다.

## 9. 운영 계획

### 9.1 요청 간격

`ebible.org/robots.txt`에는 `Crawl-delay` 선언이 없다(실측: Baiduspider 대상 `Disallow` 한 줄뿐). 자체 하한 1.0초를 유지한다. 1,189장 기준 **약 35분**이다.

### 9.2 실행 예

```bash
# 파서만 확인 (DB 미접속)
JFB_ENTRY_URL=https://ebible.org/jpnm/GEN01.htm BIBLE_TRANSLATION_TYPE=JFB \
python3 scrape_bible_to_db.py --test-book 19 --test-chapter 119

# 전권
BIBLE_TRANSLATION_ID=<tid> BIBLE_TRANSLATION_TYPE=JFB BIBLE_LANGUAGE_CODE=ja \
JFB_ENTRY_URL=https://ebible.org/jpnm/GEN01.htm \
python3 scrape_bible_to_db.py --start-book 1 --end-book 66
```

### 9.3 초안 갱신 문제

`jpnm`은 `これは翻訳の草案です`로 표기된 **개정 중 초안**이고, 조사 시점 `Last-Modified`는 `2026-08-19`였다. 이 저장소의 삽입은 missing-only라 적재 이후의 수정은 재실행으로 반영되지 않는다.

SBLM에서 확정한 **A안(수동 재적재)** 절차를 그대로 따른다. 절차와 도구는 이미 있다.

```bash
python3 scripts/check_translation_drift.py --entry-url https://ebible.org/jpnm/GEN01.htm --head-only
python3 scripts/check_translation_drift.py --translation-id <tid> --entry-url https://ebible.org/jpnm/GEN01.htm
```

삭제는 **절 → 장** 순서를 지킨다. 두 테이블에 외래 키가 없어 순서를 틀리면 절이 고아가 된다. 전체 절차는 [SBLM 설계 문서](santa-biblia-libre-para-el-mundo-scraping-design.md) 9.3절에 있다.

## 10. 대안 경로 — 文語訳

고전 문어체가 필요하거나 초안 텍스트를 피해야 한다면 `明治元訳`(구약) + `大正改訳`(신약)이 대안이다. 권리 관계는 가장 깨끗하지만 **구현 비용이 훨씬 크다.**

일본어 위키문헌 실측:

- 본문은 `창세기(文語訳)` 형식의 개별 문서에 있고, 목차 문서(`明治元訳旧約聖書`)에서 링크된다. 미작성 문서(빨간 링크) **0건**.
- **책마다 마크업이 다르다.** 창세기는 절 번호가 본문에 인라인으로 붙고(`1 元始に神天地を創造たまへり`), 시편과 마태복음은 절이 `1:1` 형식의 **개별 섹션 제목**으로 쪼개져 있다.
- 문서 제목이 USFM 코드에서 유도되지 않는다(`マタイ傳福音書(文語訳)`). 66개를 목차에서 수집해야 한다.
- 구약 底本은 1937년 인쇄본, 신약은 1950년 인쇄본으로 **판본이 섞인다.**

따라서 CLAUDE.md의 "Adding a new source" 1~8번을 **전부** 새로 해야 하고, 파서는 책별 구조 분기까지 필요하다. `jpnm`이 어댑터 재사용으로 끝나는 것과 대비된다.

**현대 구어체를 요구한 원본 문서의 취지에도 맞지 않으므로 이 설계에서는 채택하지 않는다.** 나중에 필요해지면 별도 설계 문서를 만든다.

## 12. 리스크

### 리스크 1. 공백 오염을 모르고 적재 (가장 큼)

표본의 49%가 영향을 받는데 구조 검증은 전부 통과한다. → [7.3](#73-공백-오염-검증--이-소스-전용) 전용 쿼리를 적재 **전후로** 실행하고, 구현 순서 1번을 선행 조건으로 못박는다.

### 리스크 2. CJK 범위를 넓게 잡아 한국어 파손

한글(U+AC00–D7A3)을 범위에 넣으면 NKRV 본문의 단어 사이 공백이 사라진다. 조용히 일어나고 되돌리려면 재적재가 필요하다. → 한국어 회귀 테스트를 [8](#8-테스트-설계)에 넣고, 범위 상수를 한 곳에서만 정의한다.

### 리스크 3. 미관측 USFM 클래스

10개 장 표본에서 보지 못한 표제 클래스가 다른 책에 있을 수 있다. `div.d`/`div.sp`와 같은 유형이면 조용히 오염된다. → 전권 적재 후 표제 오염 쿼리를 돌리고, 표본을 전권 스캔으로 확대한다.

### 리스크 4. 초안 본문 고착

[9.3](#93-초안-갱신-문제). SBLM과 동일한 성격이며 절차와 도구가 이미 있다.

### 리스크 5. 판본 선택 번복

이 문서는 `jpnm`을 채택하고 口語訳을 배제했다([1.2](#12-원본-문서의-법적-서술은-뒤집혀-있다)). 적재 후 판본을 바꾸면 전량 재적재다. → 착수 전에 [1.3](#13-후보-비교와-선택)의 판단을 확인받는다.

## 13. 결론

일본어 적재는 **소스 추가가 아니라 역본 추가**다. eBible 어댑터가 이미 있어 URL·HTTP·인코딩·재시도·resume·생략 절 처리까지 그대로 재사용된다.

원본 문서에서 살릴 것은 판본 후보뿐이었고, 그마저 **법적 평가가 뒤집혀 있었다.** 1순위로 제시된 口語訳은 배포처가 저작권 침해 여부를 심사 중이고, 2순위로 밀린 明治元訳/大正改訳이 실제로 권리 관계가 깨끗하다. 여기에 원본에 없던 세 번째 후보 `jpnm`을 찾았고, **퍼블릭 도메인 명시 + 현대 구어체 + 어댑터 재사용**이라는 세 조건을 모두 만족한다.

실제로 필요한 작업은 셋이다.

1. **CJK 공백 제거** — 표본 49%가 영향받는 유일한 파서 변경. 프로토타입으로 타 언어 무영향을 확인했다. 적재보다 **먼저** 해야 한다.
2. **역본 등록** — 5곳. `version` 토큰이 `jpnm`이라야 eBible 세 번째 역본이 구분된다.
3. **DB 시드** — CHECK 제약 1개, `bible_translation` 1행, `bible_book` 66행(`ul.tnav` 출처), **`bible_book_description` `ja` 66행 신규**. 일본어 역본이 DB에 없어 SBLM보다 작업이 많다.

착수 전 확인이 필요한 사항은 하나다 — **판본 선택**([1.3](#13-후보-비교와-선택)). 나머지는 결론이 나 있다.
